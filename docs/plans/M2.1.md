# M2.1 — Evaluator, compliance kernel, validator

Status: **draft, awaiting approval.** No application code is written until this plan is approved.

Features in scope (`06-features.md`): **F-010** Evaluate an existing mix (compliance, cost, data quality) and **F-011** Independent validator. Also the characteristic schema/resolver half of `04-phases.md` M2.1 (layering, unit normalization, hard-limit rejection, requested vs achieved), which F-014/F-015 (M3.1) build on. Spec refs: `01-domain.md` §3 (pipeline), §3.1 (model governance, validator), §7 (tests), §14.1 (states); `02-codes.md` §3 (Both-mode merge), §4–5 (seeds, cross-code cement check); `07-characteristics.md` §1.3, §4.1, §4.5, App. E; `05-appendices.md` App. B (fixtures).

## 1. Business objective

Give a QC engineer an honest, reproducible answer to "does this existing mix meet the requirements, what does it cost, and how good is the data behind that answer?", and make sure **no number reaches the user unless an independent second implementation agrees with it**. This is the engine every later milestone stands on (baselines, manual edits, the optimizer, the PDF), so correctness and traceability matter more than screens.

## 2. Scope

**In scope**

1. **Evaluate kernel** (`packages/engine`, pure, no I/O, no optimizer code). Input: an immutable **evaluation snapshot** (requirements, ruleset mode, project overrides, the resolved rules with their versions, proportions, material data with test versions, prices, settings). Output: an **evaluation report** with a trace entry for every computed value (inputs, formula, rule and clause). Steps, per `01-domain.md` §3:
   - **Resolve requirements** with the existing resolver (ACI / JS / BOTH, PROJECT tighten-only). Missing or null limits are reported as such; **missing is never "no limit"** and never a pass.
   - **Required average strength f'cr**: basis conversion through `strength.basis_map`, ACI 301 §4.2.3.3 **no-data** equations (no strength records exist before M4.2, so the statistical branch is implemented and tested but not reachable from stored data), each ruleset computed, higher governs, `safety_margin_mpa` added.
   - **Absolute volume** with SSD specific gravities, admixture volume, entrapped/entrained air; **yield** vs 1.000 m³ (± 0.005 default); **w/cm, binder, SCM fraction, admixture dosage**.
   - **Compliance checks** for every resolved requirement for which the data exist: max w/cm, min binder, min f'c vs the specified strength, **chlorides** (water-soluble Cl⁻ as % of cementitious from aggregate, water and admixture data), **cement property check by mill properties, not labels** (`02-codes.md` §5: C₃A for S1/S2/S3, SCM presence for S3 option 1), SCM limits, air for F classes, prohibitions, NMAS information rows. A check whose data are missing is **"not evaluated: <named blocker>"** with `INPUT_MISSING`.
   - **Strength adequacy, reported separately from compliance**: no plant model exists yet, so it is "no model", plus the ACI 211.1 T6.3.4(a) **baseline** w/c for f'cr as `MODEL_BASELINE` + `TRIAL_REQUIRED`. Never presented as compliance.
   - **Water-demand baseline** (ACI 211.1 T6.3.3 interpolated, reduced by the admixture's dosage-table water reduction) as information next to the design's actual water (`MODEL_BASELINE`); the engine states that it does not predict plant water demand.
   - **Cost** = Σ kg × JOD/kg delivered at the plant at a stated price date or snapshot, with a breakdown; unavailable / ambiguous / not-convertible prices make the cost **incomplete with the missing line named**, never zero.
   - **Data quality** per material: no test, expired or "limit not configured", declared-only key values (`INPUT_USER_DECLARED`), stale or missing price, unverified rules used (`RULE_UNVERIFIED`; today every rule is unverified, and the report says so).
2. **Characteristics (engine side)**: the Zod schema of App. E, layer merge (CODE → PROJECT → request → profile family → plant → tenant → engine defaults; more specific replaces the same key), unit normalization, **rejection of any characteristic that would loosen a CODE_HARD / PROJECT_HARD limit** (with rule, clause and allowed bound), `USER_SPECIFIED` rows, and **requested vs achieved** for the characteristics evaluable from given proportions (`wcm`, `binder_kg`, `cement_kg`, `scm`, `water_kg`, `sand_ratio_pct`, `agg_share_pct`, `agg_kg`, `paste_l`, `fm_combined`, `passing_pct`, `fresh_density`, `max_cost`, `extra_margin_mpa`, `fcr_mpa`). The API exposes the same rejection (`POST /api/characteristics/validate`), so the form cannot be bypassed. Degrees-of-freedom, conflict diagnostics, the optimizer rows and the UI panel stay in M3.1.
3. **Independent validator** (`packages/validator`): `validateEvaluation(snapshot, report)` **recomputes from the snapshot with its own arithmetic** (volume, w/cm, binder/SCM, chlorides, every limit comparison, cost, characteristic achieved values, availability) and compares every figure in the report and trace; any difference beyond tolerance, any missing trace entry, any claimed "pass" it cannot reproduce is a **hard failure that overrides the evaluator**. It imports no optimizer code (lint + dependency-cruiser already enforce this) and none of the evaluator's calculation code; it shares only the rules resolver (see ADR 0007) and decimal helpers.
4. **Lifecycle foundation (ADR 0007)**: the full §14.1 state graph as pure code (`canTransition` with named evidence), enforced server-side for the transitions that exist now (`draft → evaluated`, legacy attestation `draft/evaluated → approved/in_production`); all others are rejected with a clear "available from M4.x" reason. Illegal-transition tests cover every state pair.
5. **Persistence and API**:
   - `design_evaluations` (immutable): snapshot, report, validator result, rule versions, price basis, evaluator/validator versions, who/when.
   - `POST /api/designs/:id/evaluate` (QC Manager / QC Engineer, `design.write`): builds the snapshot from the stored design, runs evaluator then validator, stores both. **Validator pass + minimum data present** → `draft → evaluated` (failures of compliance are shown, not hidden: a mix can be `evaluated` and non-compliant). Validator failure or missing minimum data (SG for every line) → the design stays `draft` and the blockers are named.
   - Legacy-attested designs keep their state; evaluating them clears "evaluation pending" and, if any hard check fails, **raises a revalidation flag** (visible in the Library) as promised in M1.3.
   - `GET /api/designs/:id/evaluations` (+ detail). Cost figures are removed from the response for roles without `cost.view`.
6. **UI (functional, not final)**: Library design sheet gets an **Evaluate** action and an **Evaluation** tab: header verdict chips (validator verified / not, evidence statuses), key figures (yield, w/cm, binder, f'cr), the checks list (status icon + text, value, limit, source badge, clause), strength adequacy block, cost block (cost-visible roles), data-quality list, requested-vs-achieved block, and "revalidation needed" badge. The full bilingual compliance table with traceability popovers and cost baselines is **F-012/F-013 in M2.2**.
7. **Fixtures (App. B) and tests**: fixture schema + runner; evaluate fixtures reproduce volume/w/cm/binder/cost/compliance within tolerance; validator corruption suite; property tests; ≥ 90 % coverage on engine and validator.
8. **Seeds touched**: only engineering parameters this milestone needs and has a defensible default for (yield tolerance from the spec); everything else needed is read from existing rules. Missing inputs surface as named blockers.

**Explicitly excluded**

- The optimizer, design mode, rounding, guardrail rows, DoF meter, conflict diagnostics, the Studio and characteristics panel (M3.x); profiles (M3.3).
- Strength models and results, trial batches, batch weights/moisture conversion, PDFs (M4.x/M5.2). The statistical f'cr branch is built but unreachable until strength results exist.
- The manual mix editor, cost baselines, savings ledger and the polished compliance table (M2.2).
- Approval of designs by Khalta (M4.1): evaluation never approves anything.
- Hot-weather, grading-envelope and air-entrained design checks whose seed values are not on file (reported as "rule not on file", never as pass).

## 3. Assumptions

- All 79 not-on-file rule values stay not on file; ACI seeds remain `verified: false`. Every evaluation therefore carries `RULE_UNVERIFIED`, and results are provisional engineering information until a QC Manager verifies the rules.
- Imported designs carry **kg/m³ SSD** (Appendix D); evaluation uses the material's **current test** (SG, absorption, chlorides, C₃A…) and records the test version in the snapshot. A newer test later makes the stored evaluation "inputs changed" (no automatic re-evaluation until M5.1).
- Air content is taken from the design's requirements if present; otherwise the ACI 211.1 entrapped-air value for the NMAS is used and labelled `MODEL_BASELINE`; entrained air is not assumed for F classes (not on file).
- Prices: the live price in force on the evaluation date at the design's plant (`priceAt`, preferred supplier); a stored snapshot can be chosen instead. Money uses the exact decimal helpers; per-kg conversion rules from M1.2 apply (m³ prices "need density").
- Tolerances: yield ± 0.005 m³ (spec); the fixture tolerance ± 0.002 m³ (spec); the near-limit warning percentage and the safety margin are **tenant settings with no invented defaults** (unset: no near-limit warnings and zero margin, both stated in the report).
- Evaluation mode for stored designs defaults to **BOTH**; the user may pick ACI or JS per run (see Q1).

## 5. Engineering-correctness risks

| Risk                                                                                | Mitigation                                                                                                                                                                                                                       |
| ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A missing limit, test or price silently becomes a pass or zero                      | Every check has a tri-state result (`pass` / `fail` / `not_evaluated` with the blocker); aggregation rules forbid "compliant" unless every governing check evaluated and passed; types make `null` unrepresentable as a number   |
| Evaluator and validator share a bug                                                 | The validator is a separate implementation (own arithmetic, own comparison code, no import of evaluator internals); corruption tests alter the report, trace, rounding and inputs; fixtures computed by hand and checked in both |
| Wrong volume basis (SSD vs oven-dry), wrong unit (L vs kg), wrong SG for admixtures | All inputs are SSD kg/m³; litre quantities were converted at import with the SG on file and the original is kept; volume tests with SSD, dry and wet-of-SSD aggregates; trace shows each material's SG and its test version      |
| Cement label trusted instead of properties                                          | The sulfate check reads `c3a_pct` and SCM presence; "C₃A not on file" is a named blocker; tests with a Type-V-named cement lacking C₃A                                                                                           |
| f'cr misapplied (cube vs cylinder, margin, data/no-data branch)                     | Hand-computed vectors for each branch and boundary (21/35 MPa), basis conversion tests, Both mode takes the higher; the statistical branch is tested with synthetic records but unreachable from stored data                     |
| Both mode weaker than either code                                                   | Property test over generated rule sets; evaluation records which code governs each limit                                                                                                                                         |
| User characteristic loosens a hard limit through the API                            | Rejection lives in the shared resolver used by API and engine; API test posts loosening payloads for every limit-backed characteristic and expects the same rejection as the UI                                                  |
| Strength adequacy mistaken for compliance                                           | Separate block and separate evidence statuses (`MODEL_BASELINE` + `TRIAL_REQUIRED`); the compliance verdict never includes it; UI labels it "not a compliance result"                                                            |
| Stored evaluation silently stale after a test/price/rule change                     | The snapshot records versions; the UI shows "inputs changed since this evaluation" by comparing versions (no recomputation)                                                                                                      |
| Cost leak to roles without `cost.view`                                              | Cost fields are stripped server-side for those roles; test per role                                                                                                                                                              |
| Illegal state transitions                                                           | Pure transition table + server enforcement + append-only transitions (already at the database level); a test per illegal pair                                                                                                    |
| Evaluation performance on large imports                                             | Pure functions on in-memory snapshots; benchmark (200 designs evaluated + validated in a few seconds)                                                                                                                            |

- **API:** `POST /api/designs/:id/evaluate`, `GET /api/designs/:id/evaluations[/:evalId]`, `POST /api/characteristics/validate` (read-only POST); `/api/designs` list gains `needsRevalidation`; settings extension.
- **Engine (pure):** `evaluate/`, `characteristics/`, `lifecycle.ts`, fixtures runner, ACI 211.1 interpolation helpers; **Validator:** `validateEvaluation` and its own arithmetic module.
- **UI:** Evaluate action + Evaluation tab in the design sheet; "revalidation needed" chip and filter in the Library; Settings fields.
- **RBAC:** reuses `design.write` (evaluate), `library.read`, `cost.view`; no new capabilities.

## 7. Verification strategy

- Definition of Done commands green; zero serious axe violations; `pnpm screens` AR/EN × 1440/1024/390 reviewed (no pass shown without evidence, units on every number, clause badges, "not a compliance result" label on strength adequacy, cost hidden for cost-blind roles).
- **Evaluator tests:** hand-computed vectors per step (f'cr branches and boundaries, volume/yield, w/cm/binder/SCM, chlorides, sulfate cement check, ACI 211.1 interpolation, cost with each price state), every tri-state outcome, trace completeness; **evaluate fixtures** (≥ 4) reproduce expected volume (± 0.002), w/cm (± 0.001), cost (± 0.001) and compliance exactly.
- **Property tests (fast-check):** volume additivity (scaling a material changes volume by its absolute volume), cost monotonic in every price, tightening a limit never turns a fail into a pass, Both never less strict than either code, evaluation deterministic (same snapshot → byte-identical report), characteristic merge idempotent and "more specific wins".
- **Validator tests:** a corruption suite (altered volume, w/cm, binder, chloride, cost, a claimed pass, a missing trace entry, a changed limit, a changed SG, rounding) is detected **without reading the evaluator's flags**; clean reports pass; a dependency test proves no import of evaluator calculation or optimizer code.
- **Characteristics tests:** layering precedence, unit normalization, every limit-backed characteristic rejected when it loosens (engine and API), requested-vs-achieved for each supported key.
- **Lifecycle tests:** every legal and illegal transition pair; server rejects illegal ones; legacy-attested designs keep state when evaluated and get the revalidation flag when a hard check fails.
- **API tests (real Postgres):** evaluate flows (draft → evaluated, blockers when SG missing, validator failure keeps draft, attested design flag), immutability of stored evaluations (database level), RBAC matrix, plant scoping (404), cost stripping by role, audit rows, performance.
- **Coverage:** engine and validator ≥ 90 % (enforced).
- **Verification note** (in `docs/progress.md`): tests prove the arithmetic, tri-state logic, traceability and independence checks as implemented. They do **not** prove any rule value matches ACI/JS (all unverified), that the ACI 211.1 baseline predicts your plant, or that a design is acceptable to produce; nothing here approves a mix.

## 8. Rollback / migration

Additive migration (one new table, one bookkeeping column). Rollback = revert the commits and drop the table/column on dev databases; stored evaluations are derived data and can be regenerated from the designs.
