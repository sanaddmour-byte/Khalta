# M5.1 — Savings pilot and proactive insights

Status: **approved with the default answers; built (2026-10-03).**

Features in scope (`06-features.md`): **F-026** Savings ledger (theoretical / approved / realized), **F-027** Proactive insights inbox and daily digest. Spec refs: `01-domain.md` §8 (proactive engine, noise and load control), §14.2 (savings ledger), §14.3 (change classes and revalidation), §14.1 (suspension edges); `03-ui.md` §H (Insights Inbox), §I (Savings); `04-phases.md` M5.1 ("pg-boss workers, triggers (§8), debounce/dedupe, inbox, Savings screen, approved/realized states. Done: one controlled pilot reconciles baseline → approval → actual volume → realized saving").

## 1. Business objective

Turn the library into something that watches itself. When prices, tests, rules or strength results change, Khalta says what it means for approved designs — a cheaper trial-only variant worth trying, a test that expired, a design that now fails a check, a result below the acceptance criterion — and it keeps the three kinds of savings apart so the first pilot can show, with the same price snapshot on both sides, how much was actually saved on produced volume. Nothing changes state by itself except where the spec says a QC person decides.

## 2. Scope

**In scope**

1. **Workers (pg-boss).** A `worker` entry (`apps/api/src/worker.ts`, same image) running pg-boss on the existing PostgreSQL (its own schema; no Redis); an in-process mode for dev, tests and e2e. Jobs are idempotent, retried with back-off, audited as `system`, and carry a singleton key where the spec says so. Queue health (last run, failures) is visible to admins.
2. **Triggers (§8) built in this milestone:**
   - **Price change** → one debounced job per plant per edit burst (singleton key, 15-minute delay) re-optimises each `approved` / `in_production` design at that plant (the M3.1 optimizer, same materials, current prices); a result that is validator-passed, compliant and cheaper than the design **at the same snapshot** becomes a _theoretical opportunity_. Only if saving ≥ the tenant threshold (default 0.250 JOD/m³) or annual ≥ 1,000 JOD.
   - **Test expired / stale prices** → nudge insights (lists of expired tests and stale cells), info severity; expired key tests block new approvals that use them (already enforced by the M4.1 evidence gate; the insight names them).
   - **New material test** → re-evaluate affected designs; within tolerance = info; drift beyond tolerance, source change, or any failed check (yield drift > 2 %) = high/critical insight naming the design and the change (§14.3).
   - **Rule or project change** → re-evaluate dependent designs; an insight lists the compliance impact (new failures, newly provisional) and the designs that may need revalidation.
   - **Result below acceptance criteria** (a strength result for an approved / in-production design under f′cr per the trial criteria, or a failed trial batch) → immediate **critical** insight to QC managers.
   - **Nightly 02:00 Asia/Amman sweep** runs every trigger once, creates the day's **digest**, and takes the month-close price snapshot (see 5).
3. **Insights (F-027).** `insights` table: type, severity (info / medium / high / critical), plant, design, `dedupe_key` = hash(design, trigger, inputs), status (`open`, `snoozed`, `dismissed`, `accepted`, `expired`), payload (what changed, evidence, named inputs), theoretical saving fields where relevant. An open match is **updated, not duplicated**; an insight **expires when its inputs change**. Roles see their plants' insights; cost figures only with `cost.view` (the insight text for cost-blind roles omits them).
4. **Inbox screen** (the Insights nav item stops being a placeholder): triage list with severity, type, plant, **theoretical** saving in JOD/m³ and JOD/yr (labelled), filters, **Accept** (creates a prefilled **trial-only draft** via the optimizer request path, never a design above `trial_candidate`; capability `insight.accept` → QC manager), **Dismiss** with a reason, **Snooze** (1 day / 1 week). Only critical items interrupt (a banner in the shell for QC managers); everything else is inbox and digest.
5. **Daily digest.** One stored digest per day per tenant (counts by severity and type, top opportunities, expired items, open criticals) shown at the top of the inbox and available as `GET /api/insights/digest`. **No e-mail** in this milestone (there is no mail infrastructure); stated in the UI.
6. **Suspension and reinstatement (§14.3, §14.1).** Turn on the M5.1 edges: QC manager **suspends** an `approved` / `in_production` design (reason + e-signature, from a critical insight or by hand), **reinstates** it (same), through the existing lifecycle service and database guard. A suspended design is blocked from release and shows on the Library. Nothing suspends automatically.
7. **Savings ledger states (F-026, §14.2).** Extend `savings_entries`:
   - **Theoretical:** unchanged (and now also created from accepted insights).
   - **Approved:** when a replacement design (a new version that supersedes the baseline) is **approved**, an entry compares baseline vs approved cost per m³ at the **approval-date price snapshot** (the same snapshot for both).
   - **Realized:** per month, Σ (baseline cost − approved cost, both at **that month's price snapshot**) × **actual produced volume of the replacement**. Needs recorded volumes and a snapshot for the month; missing either blocks the entry and says which.
     Totals never mix states; every figure shows its state, period, volume (eligible vs actual) and price snapshot.
8. **Production volumes.** Entry API and screen (per design, plant, month, m³; capability `lab.enter` or a new `volume.enter` for plant managers of that plant and QC roles; CSV paste for a month). Append-only with a correction note; the existing `production_volumes` table is used.
9. **Savings screen.** Three columns (theoretical / approved / realized) with KPIs, period selector, eligible vs actual volume, price snapshot used, drill-down to each entry and its calculation trace; theoretical figures stay labelled "not savings yet".
10. **The pilot.** A documented, repeatable **controlled pilot** scenario (test and e2e, SYNTHETIC data): baseline design at price snapshot A → price change → insight with a cheaper variant → Accept → trial → pass → approval of the variant → two months of volumes → realized saving that **reconciles to the cent** against an independent hand calculation in the test. The real pilot waits for your plant data.
11. **API.** `GET /api/insights`, `POST /api/insights/:id/{accept,dismiss,snooze}`, `GET /api/insights/digest`, `GET /api/system/jobs` (admin); `POST /api/designs/:id/{suspend,reinstate}`; `GET/POST /api/production-volumes`; savings ledger endpoints extended with state and period. Audit on every mutation; cost-blind roles never receive cost.
12. **i18n, tests, docs.** EN/AR strings (Arabic drafts in `docs/i18n-review.md`); ADR 0013 (pg-boss workers, debounce/dedupe, insight lifecycle, realized-savings calculation); engine tests for the pure parts (opportunity eligibility and thresholds, dedupe key, realized/approved saving arithmetic with property tests: same-snapshot comparisons never credit price movement, state totals never mix); API tests with real Postgres (each trigger, debounce, dedupe-update, expiry, RBAC and plant scope, cost-blindness, accept never exceeds `trial_candidate`, suspension rules, ledger states and blocked cases); worker tests with pg-boss against the test database; e2e with axe (price change → insight → accept → …); screens EN/AR × 1440 / 1024 / 390.

**Explicitly excluded**

- Strength model fitting, s refit, cement-reduction opportunities and low-strength model alerts (M5.2); **season-switch drafts** and **material-unavailable substitutes** (listed in §8 but they need season dates and availability data from you; deferred, stated in the UI); e-mail or push delivery of the digest; CSV export for batch plants (M6.1); automatic suspension; any automatic approval.

## 3. Assumptions

- The worker may run inside the API process in dev/test and as a separate service in staging; pg-boss uses the same `DATABASE_URL` and creates its own schema.
- "Re-optimise an approved design" means: the same plant, requirements and characteristics as the design's stored request, current prices, M3.1 optimizer; if the design came from a legacy import (no stored request), the opportunity uses its requirements and the plant's materials and is labelled with that source.
- A month's price snapshot is taken by the nightly job on the first run after month end (the latest live prices that day), unless a QC manager already created a named snapshot for that month.
- Insight thresholds are the existing tenant settings (`insightMinSavingJodPerM3` 0.250, `insightMinAnnualJod` 1,000).

## 5. Engineering-correctness risks

| Risk                                                       | Mitigation                                                                                                                                                           |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Market price movement booked as optimization               | Baseline and variant always priced at the **same** snapshot; property test; the ledger stores both costs and the snapshot id                                         |
| An insight silently changes a design or approves something | Accept creates only a trial-only draft at `trial_candidate`; suspension/reinstatement are QC-manager acts with e-signature; no worker path changes a design's status |
| Alert fatigue                                              | Thresholds, dedupe-update, expiry, debounce, only criticals interrupt (tested)                                                                                       |
| A job runs twice or crashes mid-way                        | Idempotent jobs keyed by dedupe, pg-boss retries/back-off, transactions per design; test of a double run                                                             |
| Realized saving overstated                                 | Needs recorded volumes **and** the period's snapshot; blocked and named otherwise; reconciliation test against a hand calculation                                    |
| Stale or provisional figures presented as firm             | Every figure carries state, period, snapshot and the provisional flag (rules unverified); theoretical is labelled                                                    |
| Cost leaks to cost-blind roles via insights or the digest  | Shaped server-side per role; API tests per role                                                                                                                      |
| Worker load                                                | One job per plant per burst, per-design transactions, time budget per optimizer run (existing), nightly sweep batched                                                |

## 6. Schema / API / UI impact

- **Schema (0022+):** `insights`, `insight_events` (append-only history), `daily_digests`, ledger columns (`state` widened to theoretical/approved/realized, period, volume, both costs, snapshot ids, source insight), `production_volumes` extended with a correction note; pg-boss manages its own schema.
- **Engine:** `insights/` (eligibility, dedupe key, severity rules), `savings/` (approved and realized arithmetic with decimals), pure and tested.
- **API/worker:** workers and routes as above.
- **UI:** Insights inbox, critical banner, Savings three-column screen, production volumes entry, suspend/reinstate in the lifecycle section.

## 7. Verification strategy

- Definition of Done commands; engine coverage stays ≥ 90 %.
- **Phase gate as a test:** the controlled pilot reconciles baseline → approval → actual volume → realized saving exactly.
- Trigger tests (each row of §8 built here), debounce and dedupe-update, expiry, double-run idempotency, RBAC and cost-blindness per role, suspension edges (and that nothing else can suspend).
- e2e and screens as in scope item 12.
- **Verification note** (in `docs/progress.md`): tests prove the triggers, thresholds, de-duplication, state separation and the reconciliation arithmetic as implemented. They do **not** prove that a theoretical opportunity will survive a trial, that your volumes and prices are right, or that the SYNTHETIC pilot resembles yours.

## 8. Rollback / migration

Additive tables and columns; the existing ledger rows stay `theoretical`. Rollback = revert the commit and stop the worker; no existing record changes meaning.
