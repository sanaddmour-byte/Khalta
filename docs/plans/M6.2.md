## 1. Business objective

Make it safe to put real plant data in Khalta: a production build that is smaller and stricter than staging, a worker that runs as its own service, nightly backups that are verified rather than hoped for, a restore that has actually been performed and timed, and runbooks a person on call can follow at 2 a.m. Nothing here changes engineering or governance behaviour.

## 2. Scope

**In scope**

1. **Production image.** Replace the staging shortcut ("API runs its TypeScript through tsx; compile in M6.2") with a compiled build: the API, the worker and the migrations are bundled (esbuild) into `dist/`, the runtime image carries only production dependencies, **Chromium and Arabic-capable fonts for the PDF submittal** (today's image has none), `postgresql-client` for the backup job, a non-root user, and the same `HEALTHCHECK`. One image, two commands: `node dist/server.js` (`api`) and `node dist/worker.js` (`worker`). Verified here by running the bundle against a local PostgreSQL and the existing smoke script; the container build itself runs in CI (this sandbox has no container daemon, stated in the verification note).
2. **Environment and configuration.** A single documented variable contract (`docs/runbooks/production.md`): `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `APP_BASE_URL`, `PDF_BASE_URL`, `BACKUP_BUCKET_*`, `NODE_ENV=production`, `TRUST_PROXY=1`. In production the API **refuses to start** on unsafe settings (demo seed allowed, a non-https origin, a short secret, `JOBS_IN_PROCESS=1` together with a separate worker is warned) and secure cookies are enforced; tests prove each refusal. Railway: `staging` auto-deploys from `main`, `production` is promoted by hand; services `api` and `worker` (same image, different start command), managed PostgreSQL. **I create nothing on Railway until you say go.**
3. **Readiness and observability.** `/health` stays a cheap liveness check; a new `/ready` checks the database and that every migration is applied, for the platform's deploy gate. Structured pino logs with request ids (already present) are documented with the fields to alert on; admins get `GET /api/system/backups` beside the existing `GET /api/system/jobs`. Security headers for the API and the static app (HSTS in production, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, a restrictive `Content-Security-Policy` that the app and the PDF route still work under, tests included).
4. **Backups.** A `backup` job in the worker (nightly 01:30 Asia/Amman) runs `pg_dump -Fc` of the whole database, writes a manifest next to it (SHA-256, size, PostgreSQL version, migration count and last migration, application version, row counts of the safety-critical tables: designs, design transitions, audit log, rules, savings entries, batch instances), uploads both to an **S3-compatible bucket** under `khalta/<environment>/<yyyy>/<mm>/…`, re-reads the object to verify its hash, and records the run (`backup_runs`: start, end, status, key, bytes, hash, error; additive migration). **Retention: 30 days**, but never fewer than the 7 most recent verified backups. A failed or missing backup is visible: admins see it on `/api/system/backups`, `/ready` reports "backup stale" past 26 hours (informational, never taking the service down), and the run writes an audit entry. A local-directory storage adapter is used by tests and by the drill.
5. **Restore.** `scripts/restore` (CLI): list backups, fetch one (default: the newest verified), check its SHA-256 against the manifest, `pg_restore` into a **named target database that is not the live one** (it refuses the production `DATABASE_URL` unless an explicit flag and a typed confirmation are given), run the migrations check, and run the **verification** (`scripts/restore-verify`): table presence, migration journal equal to the manifest, and **row counts equal to the manifest** for the critical tables, plus an application boot against the restored database and the smoke script.
6. **The restore drill — executed.** In this session: load the SYNTHETIC demo dataset into a scratch database, run the backup to the local-directory store, restore into a fresh database, verify, boot the API on it and run the smoke test, and record the real timings, sizes, and counts in `docs/runbooks/restore-drill-2026-10-03.md`. The same drill is repeated on Railway at go-live (listed in the go-live checklist); I do not claim a Railway drill before it happens.
7. **Runbooks** (`docs/runbooks/`): `production.md` (environments, variables, deploy, **promote**, rollback, migrations, secrets and rotation, access), `backup.md`, `restore.md` (step by step, the commands used in the drill), `incident.md` (health and readiness failing, worker stuck, queue backlog, failed migration, bad deploy, lost secret, suspected data corruption, restore decision tree), `go-live.md` (a checklist ending in the explicit approvals only you can give). RPO and RTO stated and measured against the drill.
8. **CI.** A workflow that builds the production image, starts it with a PostgreSQL service, and runs the smoke script (so the first container build is a CI check, not a deploy surprise); the existing job keeps running.
9. **Tests, docs.** Unit and API tests (config refusals, `/ready`, security headers, backup job with the directory adapter: manifest, hash verification, retention including the keep-last-7 rule, failure recording, RBAC and cost-blindness of `/api/system/backups`), a **restore round-trip test** (dump → restore into a fresh database → counts equal → API starts) in the API tests, e2e smoke of the production bundle's login path; ADR 0017 (production topology, compiled build, backup and restore design); `docs/progress.md` with the verification note.

**Explicitly excluded**

- Creating or changing anything on Railway, a real domain, a real bucket or credentials (until you say go); point-in-time recovery or WAL archiving (RPO is 24 h by design, stated); client-side encryption of dumps (the bucket is private with server-side encryption); e-mail or push alerts; a backup UI screen (API and runbook only); autoscaling, multi-region, blue/green; any change to engineering, governance or the data model beyond `backup_runs`.

## 3. Assumptions

- The managed PostgreSQL on Railway allows `pg_dump` over its connection string from the worker service (same private network).
- An S3-compatible bucket (AWS S3, Cloudflare R2, Backblaze B2, or a Railway bucket) with a private ACL and server-side encryption; credentials arrive as the `BACKUP_BUCKET_*` variables.
- `pg_dump` / `pg_restore` of the server's major version are installed in the image (17); this sandbox has 16, which is enough for the drill but is stated.
- The compiled bundle can load the HiGHS WebAssembly solver and Playwright Chromium at runtime (verified locally for the solver; Chromium path via `PLAYWRIGHT_CHROMIUM_EXECUTABLE`).

## 5. Engineering-correctness risks

| Risk                                                          | Mitigation                                                                                                                                                                              |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A backup that cannot be restored                              | The drill and a round-trip test; every backup is hash-verified after upload and its manifest row counts are checked on restore                                                          |
| A restore into the live database by mistake                   | The tool refuses the live URL without an explicit flag and a typed confirmation; the runbook restores into a new database and swaps                                                     |
| Compiled bundle behaves differently from the tsx build        | The same test suite runs against the bundle's smoke path; the engine and validator stay pure TypeScript compiled by the same bundler; the solver WebAssembly and Chromium paths checked |
| PDF export broken in production for lack of Chromium or fonts | Chromium and fonts are in the image; a CI step renders one Arabic and one English submittal from the built image                                                                        |
| Backups stop silently                                         | `backup_runs`, `/ready` "stale" flag at 26 h, admin endpoint, audit entry, runbook check                                                                                                |
| Secrets in logs or images                                     | Variables only at runtime; logs redact credentials; the image build has no secrets; `.dockerignore` already excludes `.env*`                                                            |
| A migration that fails during deploy                          | Migrations run before the new version takes traffic (existing); `/ready` is the deploy gate; rollback and fix-forward steps in the runbook                                              |
| Retention deletes the only good backup                        | Never fewer than 7 verified backups kept; deletion only of verified-older-than-30-days objects; tested                                                                                  |
| Over-tight CSP breaks the app or the PDF route                | Headers tested against the built app in e2e; report-only first in staging (documented)                                                                                                  |

## 6. Schema / API / UI impact

- **Schema:** `backup_runs` (additive migration, append-only).
- **API:** `GET /ready`; `GET /api/system/backups` (admin); the worker gains the `backup` job; production config refusals; security headers.
- **UI:** none beyond what exists (a note on the Settings screen is not needed; admins use the endpoint and runbook).
- **Repo:** `Dockerfile` (multi-stage, compiled), `railway.json` per service, `scripts/backup`, `scripts/restore`, `scripts/restore-verify`, CI workflow, runbooks, ADR 0017.

## 7. Verification strategy

- Definition of Done commands; engine and validator coverage unchanged.
- **Phase gate:** the restore drill executed and documented with real numbers (`restore-drill-2026-10-03.md`), plus the automated round-trip test.
- Config-refusal, readiness, headers, backup, retention and failure tests; the compiled bundle booted against PostgreSQL and passed through the smoke script (including a sign-in and a PDF if Chromium is present).
- **Verification note** (in `docs/progress.md`): tests and the drill prove the backup is complete against its manifest, the restore reproduces it, the unsafe settings are refused, and the retention rule never removes the last good backups. They do **not** prove the container image builds or runs on Railway (no container daemon here; CI and the first deploy do that), that the real bucket accepts the upload, or that the drill on Railway's managed PostgreSQL has the same timings.

## 8. Rollback / migration

One additive migration (`backup_runs`). The image and railway config are replaceable: rollback = redeploy the previous image; the backup job can be disabled with a variable; staging keeps working on the old start command until it is switched.
