# M4.1 — Library and lifecycle

Status: **draft, awaiting approval.** No application code is written until this plan is approved.

Features in scope (`06-features.md`): **F-022** Lifecycle and approval workflow with e-signature. Spec refs: `01-domain.md` §14.1 (states and gates), §14.3 (change classes), §14.4 (trial acceptance criteria); `07-characteristics.md` §2.5 (approval policy for declared values); `04-phases.md` M4.1 ("Versioned library, diff, full §14.1 state machine, trial acceptance, change classes, e-signatures; declared-values approval policy. Done: every illegal transition rejected (tested); approval blocked by unverified/null rules and four-eyes; approval blocked without lab source or QC acceptance (tested)"). Trial **batches** and strength results are M4.2 (F-023); the revalidation and suspension _triggers_ are M5.1.

## 1. Business objective

Make "approved" mean something. A design can only become approved through a named, evidenced, four-eyes path: a trial candidate → trial → QC-reviewed trial pass → approval by a QC manager who did not write it, with every governing rule verified, evidence current and the declared-values policy satisfied, all signed with a typed e-signature. Approved designs are immutable; any change is a new version that goes back through the gates, and the library shows each version, what changed and why.

## 2. Scope

**In scope**

1. **The full §14.1 state machine, server-enforced.** The graph in `packages/engine/src/lifecycle.ts` already names every edge and its evidence. This milestone turns on the M4.1 edges and gives each one a server transition service that checks the gate, stores the evidence in the append-only `design_transitions` row (with who, when, reason and the e-signature) and refuses everything else with a named reason. Active edges after this milestone: `trial_candidate → trial_in_progress`, `trial_in_progress → trial_passed`, `trial_passed → approved`, `approved/in_production/suspended → superseded`, any pre-approval state or `approved/in_production/suspended → retired`; the M5.1 edges (`suspended` entry and exit) stay disabled with "available from M5.1".
2. **Trial gates without trial batches.** Batch entry is M4.2, so the two trial edges are enforced against what exists: `trial_candidate → trial_in_progress` needs a logged trial batch and `trial_in_progress → trial_passed` needs the trial criteria met plus QC sign-off. Until M4.2 there is no way to log a batch, so those two edges report "needs a trial batch (arrives with M4.2)" in the UI; the API and gate code are complete and tested with test-only fixtures. Nothing shortcuts the trial: there is still no path from the optimizer to `approved`.
3. **Trial acceptance criteria (§14.4).** QC-configured rule parameters (kind `parameter`, seeded **unset**): slump and air tolerance, fresh density and yield band, hot-weather temperature limit, and the strength criterion (ACI 301 average ≥ f′cr or the project's stricter one). A pure `evaluateTrialAcceptance(criteria, batches)` in the engine returns per-criterion pass/fail/missing; **a missing criterion blocks `trial_passed`** and names the parameter, like the optimizer's blockers.
4. **Approval gate (`trial_passed → approved`).** All of: (a) four-eyes (approver ≠ author, API and database); (b) every governing rule the design was evaluated against is verified (a null/unverified rule blocks, named); (c) evidence is current — the stored evaluation is re-run on current inputs and the validator agrees, and no key test is expired or superseded; (d) the **declared-values policy**: with `approval_requires_lab_source` on (default), every key property (aggregate gradation, SG, absorption; cement `c3a_pct` when sulfate governs; admixture dosage response) comes from `lab_report` or `supplier_datasheet`, otherwise a QC manager must accept the declared values with an e-signature recorded in the design's evidence; (e) a typed e-signature (name, reason ≥ 5 characters) stored with the transition. A blocked approval lists every unmet gate, never just the first.
5. **E-signatures.** One reusable `esignature` object on transitions: signer, role, meaning ("reviewed and approved", "accepted declared values", "released to {plant}", "retired"), reason, timestamp, and the hash of the design version it was applied to. Append-only; the UI shows it next to the state change. (Legal weight of a typed signature is outside this build; stated in the UI.)
6. **Versioned library and diff.** "New version" copies a design (any state except draft) into the next draft version (`parent_design_id`, `version + 1`), keeping lines, requirements, characteristics snapshot and profile origins; the parent keeps its state until the new version is approved, then goes `superseded` automatically with `new_version_approved` evidence. Library design detail gains a versions list and a diff (proportions in kg/m³ and % change, requirements, characteristics, rule/test/price snapshot ids, evaluation verdict) between any two versions. Approved designs remain immutable (database trigger already forbids content edits).
7. **Release and retire.** `approved → in_production` by a QC manager or the plant manager of that plant, with e-signature; retire by QC manager decision with reason; both tested against the plant scope.
8. **Change classes (§14.3).** A pure classifier `classifyChange(oldDesign, newDesign)` labels a new version as price-only, new test within tolerance, material drift, proportion change, admixture product change or rule/spec change, and shows the class on the diff. Per policy: proportion and admixture changes **always** go through a trial (default "minor-adjustment policy = none"); the policy itself is a QC parameter (`policy.minor_adjustment`, default none, seeded unset = none). Classification is information; it never moves a state.
9. **Approval queue and library filters.** Library gets "Awaiting approval" (trial_passed) and "In trial" tabs next to the existing queue; the design sheet shows gates as a checklist (met / unmet with the reason) and the Approve button is disabled until all are met (and for the author).
10. **API.** `POST /api/designs/:id/transitions` (`{to, evidence, esignature}`; one endpoint, the lifecycle graph decides), `POST /api/designs/:id/versions`, `GET /api/designs/:id/gates?to=` (the checklist for a target state, no side effects), `GET /api/designs/:id/diff?with=` , `POST /api/designs/:id/accept-declared` (QC manager e-signature), criteria in the Rules API. RBAC: existing `trial.request`, `trial.pass`, `design.approve`, `production.release`; no cost involved. Audit on every mutation.
11. **i18n, tests, docs.** EN/AR strings (Arabic drafts in `docs/i18n-review.md`); ADR 0011 (approval gate, e-signature, versioning); engine tests (every edge legal with its evidence and illegal without; **every pair of states not in the graph is rejected**, exhaustive; trial acceptance; change classifier; property tests that no sequence of legal transitions reaches `approved` without `trial_passed` or legacy attestation); API tests with real Postgres (four-eyes, each unmet gate blocks and is named, declared-values policy on and off, immutability, version/supersede, plant-scoped release, RBAC, audit); e2e with axe (blocked approval lists gates → fix → approve with e-signature → release → new version → diff → supersede); screens EN/AR × 1440 / 1024 / 390.

**Explicitly excluded**

- Trial batch entry, strength results, batch weights and the PDF submittal (M4.2); suspension/reinstatement and automatic revalidation triggers, insights inbox, savings ledger changes (M5.1); strength models (M5.2); e-signature with an external identity provider; bulk approvals.

## 3. Assumptions

- `trial_in_progress` / `trial_passed` cannot be reached in a real tenant until M4.2 lands (no batch entry); that is stated in the UI, not hidden. Legacy-attested designs are unaffected.
- A "key property" set is the §2.5 list; a property is "declared" when its source is not `lab_report` or `supplier_datasheet`.
- "Evidence current" means: the design's stored evaluation inputs equal the current rules/test/material versions or a re-evaluation on current inputs passes the validator; if anything changed, approval asks for re-evaluation first.
- The version number is per design lineage (`parent_design_id` chain); the code stays `…-vN`.

## 5. Engineering-correctness risks

| Risk                                                | Mitigation                                                                                                                                                                                      |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A design reaches `approved` without a trial         | Only the graph's edges exist; exhaustive illegal-pair tests and a property test over random legal sequences; API refuses any other `to`; database trigger refuses status jumps not in the graph |
| Approval on unverified/null rules or stale evidence | The gate lists every unmet condition; tests for each; the approval re-checks at the moment of approval, not at button-render time                                                               |
| Declared values slip into an approved design        | Policy gate (lab source or QC acceptance with e-signature recorded in evidence); test with the policy on and off                                                                                |
| Author approves their own design                    | Four-eyes in API and DB check; tested                                                                                                                                                           |
| An approved design is edited in place               | Existing immutability trigger kept; "New version" is the only edit path; test that content updates on approved rows fail                                                                        |
| Silent trial skip for "small" changes               | Minor-adjustment policy defaults to none; classifier is information only                                                                                                                        |
| Signature appears to bind more than it does         | UI states what a typed e-signature records (who, when, meaning, version hash); legal validity is not claimed                                                                                    |

## 6. Schema / API / UI impact

- **Schema (0018+):** `design_transitions` gains e-signature columns (signer, meaning, reason, design-version hash, accepted-declared flag); `mix_designs` version/parent usage extended, supersede link; a trigger that refuses a status change not in the graph (belt and braces for the service); declared-values acceptance recorded in `recommendation_evidence`-style JSON on the transition. Additive.
- **Engine:** `lifecycle.ts` edge availability, `trial/acceptance.ts`, `changes/classify.ts`, `approval/gates.ts` (pure gate checker over a plain snapshot), all pure and tested; no change to evaluator or validator arithmetic (the gate calls the validator through the existing injection).
- **API:** endpoints in scope item 10; criteria and policy as rules (kind `parameter`).
- **UI:** design sheet gains the gate checklist, Approve/Release/Retire/New version dialogs with e-signature, versions list and diff; Library gains the two tabs.

## 7. Verification strategy

- Definition of Done commands; engine coverage stays ≥ 90 %.
- Phase gate as tests: **every illegal transition rejected**; approval blocked by unverified/null rules, by four-eyes, and without lab source or QC acceptance.
- Property: no legal sequence from `draft`/`evaluated`/`trial_candidate` reaches `approved` unless it passes `trial_passed` (or is a legacy attestation).
- API tests (real Postgres) and e2e as in scope item 11.
- **Verification note** (in `docs/progress.md`): tests prove the gates, evidence, immutability and versioning as implemented. They do **not** prove any design is safe to produce, that the trial criteria values (synthetic in tests) are the right ones for your plant, or that a typed e-signature is legally binding.

## 8. Rollback / migration

Additive columns and a trigger; existing designs and transitions are untouched. Rollback = revert the commit and drop the new columns; no data loss for existing rows.
