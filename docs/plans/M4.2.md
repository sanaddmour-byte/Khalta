# M4.2 — Lab loop and PDF

Status: **approved with defaults; built.**

Features in scope (`06-features.md`): **F-023** Trial batches and strength results, **F-024** Batch weights with moisture correction, **F-025** Bilingual PDF submittal with QR code. Spec refs: `01-domain.md` §6 (production conversion), §14.1 / §14.4 (trial gates), §9 (PDF via Playwright `page.pdf()`); `03-ui.md` §F (Design Detail: trial batch log, strength chart), §7 (PDF submittal); `04-phases.md` M4.2 ("Trial batches, strength results, `batch_instances` + `validateBatch`, bilingual PDF with watermark rule. Done: moisture tests pass; PDF renders correct Arabic (visual snapshot)").

## 1. Business objective

Close the loop between the office and the lab. A QC engineer logs a trial batch and its cylinder results against a trial candidate; the existing M4.1 gates then judge it. A batch plant operator sees what to weigh today: the approved SSD design converted to wet batch weights using the day's measured moisture, with every intermediate term shown and an independent check of the water balance. A client gets a bilingual, print-tested PDF whose watermark says "NOT APPROVED — TRIAL ONLY" unless the design is approved or in production.

## 2. Scope

**In scope**

1. **Trial batches (F-023).** Entry API and a "Trial batches" section on the design sheet for `trial_candidate` and `trial_in_progress` designs: date, measured slump, air, concrete temperature, fresh density, yield, water added on site to reach slump (information), notes. Append-only (a correction is a new batch with a "supersedes" note); plant-scoped; capability `lab.enter`. The M4.1 `trial_batches` table gains the missing columns; the first batch does **not** move the state by itself (a person presses "Start trial", as in M4.1).
2. **Strength results (F-023).** `strength_results` (`01-domain` §2): per batch (or per approved/production design), cast date, test age (days), specimen type (cylinder / cube), set id, individual specimen results in MPa; converted to the design's basis through `strength.basis_map` only for display (the raw value is stored). The M4.1 `trial_acceptance` judges the **average of the specimens at the design's test age** against f′cr; results at other ages are stored and shown, never judged. The batch row's `strength_mpa` array is replaced by these rows (migration moves nothing: M4.1 wrote it only from test fixtures).
3. **Trial acceptance view.** The gate checklist already exists (M4.1); here each criterion also shows the measured value, target and limit, and the latest batch it was judged on. Strength chart: results vs f′c and f′cr, running average of 3, acceptance line (ECharts, never mirrored in RTL).
4. **Batch weights (F-024).** Pure engine `toBatchWeights(design, moisture[])` per `01-domain` §6: oven-dry mass, wet batch mass, free-water contribution (negative when drier than SSD), batch water to add, with every intermediate term and a mass/water balance trace; absorption and total moisture are never conflated. The admixture solution-water convention is **defined, tested and stated**: admixture solids % from the material test; solution water = admixture mass × (1 − solids %); it is subtracted from batch water **only when the plant opts in** (a tenant setting, default off, because the convention differs per product). Moisture inputs are rejected when impossible (< absorption − 100 %, total > `eng.moisture.max_total_pct`) or stale (older than `eng.moisture.stale_hours`); both rules are QC parameters seeded unset: **a missing limit blocks the conversion and is named**.
5. **`validateBatch` (independent).** In `packages/validator` (no import from the optimizer or evaluator calculation modules): recomputes the conversion from the raw inputs and checks the water balance (Σ batch masses = SSD masses + Σ moisture − added water), the sign of every term, the totals, and operational limits. A mismatch is shown and the batch weights are not offered. Result saved with the `batch_instance`.
6. **`batch_instances`.** Stored production corrections (design id + version, plant, timestamp, moisture inputs, full conversion trace, validator result, who). **Never new design versions**; the approved SSD design stays immutable. Allowed for `approved`/`in_production` designs (and for trial candidates/in-progress designs, labelled "trial batch weights"). Capability `lab.enter` (plant managers: own plants).
7. **Batch weights UI.** On the design sheet: moisture entry per aggregate (and admixture), the conversion trace, the validator verdict, "Save as today's batch instance", history of batch instances; the Studio "SSD ⇄ batch" toggle from `03-ui` §B is **not** in this milestone (Studio candidates have no stored design to convert).
8. **PDF submittal (F-025).** `GET /api/designs/:id/submittal.pdf?lang=ar|en|both` renders HTML with Playwright `page.pdf()`: letterhead and plant details (tenant setting; falls back to a plain text header when unset), design code + version + lifecycle state + QR code linking to `APP_BASE_URL/library/<id>`, sections requirements, materials with sources and test dates, proportions (SSD, plus the latest batch instance if any), compliance table with classes, evidence chips and clause references, strength evidence, gradation chart, f′cr derivation, **Specified characteristics block** (values and origins, declared values marked, 07 §7), approval block (names, dates, e-signatures from M4.1, or the legacy attestation reference), disclaimer. A4, print-tested. **Watermark rule:** any state other than `approved` or `in_production` carries a diagonal "NOT APPROVED — TRIAL ONLY / غير معتمد — للتجربة فقط" watermark; it cannot be turned off. A superseded or retired design carries "SUPERSEDED/RETIRED" instead. Cost is never printed (cost-blind by design). Roles: anyone with `library.read`; export is audited.
9. **Fonts and Arabic.** IBM Plex Sans Arabic / Plex Sans self-hosted and embedded; bidi and shaping verified by a **visual snapshot** of the Arabic PDF page (first page rasterised and compared with a stored baseline, tolerance stated) plus a text-extraction check that Arabic strings are present and in logical order.
10. **API.** `POST /api/designs/:id/trial-batches`, `GET …/trial-batches`, `POST /api/trial-batches/:id/strength-results`, `GET …/strength-results`, `POST /api/designs/:id/batch-weights/preview` (read-only conversion + validator), `POST /api/designs/:id/batch-instances`, `GET …/batch-instances`, `GET /api/designs/:id/submittal.pdf`. Audit on every mutation and export.
11. **i18n, tests, docs.** EN/AR strings (Arabic drafts in `docs/i18n-review.md`); ADR 0012 (batch conversion conventions, independent batch validator, PDF pipeline and watermark rule); engine tests (conversion golden cases hand-computed, property tests: mass/water balance closes for any inputs, drier-than-SSD yields negative free water, conversion monotonic in moisture, SSD → batch → SSD round trip); validator tests that deliberately corrupt conversions; API tests with real Postgres (RBAC, plant scope, append-only, acceptance on real batches replacing the fixtures, batch instance never changes the design, PDF watermark by state, audit); e2e with axe (log batch + results → start trial → pass → approve → batch weights → PDF download); PDF visual snapshot (Arabic) and screens EN/AR × 1440 / 1024 / 390.

**Explicitly excluded**

- Statistical f′cr from strength history, strength models, low-strength alerts, β calibration (M5.2): results are stored and shown; **the evaluator's f′cr does not change**. Suspension triggers and insights (M5.1); CSV export for batch plants / ERP (M6.1); the Studio SSD ⇄ batch toggle; photo/lab-report attachments for batches; PDF e-mail sending.

## 3. Assumptions

- A design's test age and f′c basis come from its stored requirements; the specimen average is taken over the results at that age for the **latest** trial batch.
- Moisture is entered as **total moisture %** per aggregate (as measured on the dried-sample method); absorption comes from the material test. Fines in SSD basis are as in §6.
- Chromium is available to the API process (the spec's Docker image); in tests and e2e the pre-installed Chromium is used.
- The QR code targets the live library URL; it needs `APP_BASE_URL` (falls back to the request origin in dev).

## 5. Engineering-correctness risks

| Risk                                                        | Mitigation                                                                                                                           |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Wet mass mistaken for SSD mass (or moisture for absorption) | Distinct named terms in the trace; hand-computed golden cases; property: SSD → batch → SSD round trip; independent `validateBatch`   |
| Stale or impossible moisture reading used in production     | Rejected against QC limits; stale readings named; missing limits block                                                               |
| A production correction silently becomes a design change    | `batch_instances` are separate rows; the design row is untouched (test); no API path edits proportions                               |
| Trial pass judged on the wrong specimens                    | Only results at the design's test age, only the latest batch, specimen count shown; missing results block `trial_passed` (M4.1 gate) |
| Unapproved design circulates as approved                    | Watermark is rendered by the server from the design's state, not a user option; test per state; "superseded/retired" wording         |
| Arabic PDF mis-shaped or reversed                           | Embedded Arabic font, `dir` and lang attributes, visual snapshot and extraction check                                                |
| Costs leak through the PDF                                  | The PDF template has no cost fields; test greps the extracted text for currency/cost labels                                          |
| Admixture solution water double-counted                     | Opt-in setting, default off; both conventions tested; the trace names which was used                                                 |

## 6. Schema / API / UI impact

- **Schema (0020+):** `trial_batches` extended (slump, air, temperature, fresh density, yield, water added, notes, supersedes); `strength_results`; `batch_instances`; settings for letterhead and the admixture convention; append-only triggers. Additive.
- **Engine:** `production/toBatchWeights.ts`, `trial` acceptance reads rows instead of the array, pure and tested. **Validator:** `validateBatch` (own arithmetic, no optimizer or evaluator calc imports; dependency-cruiser rule extended).
- **API:** endpoints in scope item 10; Playwright PDF renderer behind a small interface (stubbed in unit tests).
- **UI:** design sheet: Trial batches, Strength (chart), Batch weights, "Submittal PDF" button (AR / EN / both).

## 7. Verification strategy

- Definition of Done commands; engine coverage stays ≥ 90 %.
- Phase gate as tests: **moisture tests pass** (golden, property, rejection of impossible/stale/missing-limit inputs); **PDF renders correct Arabic** (visual snapshot + extraction).
- Corruption tests for `validateBatch`; watermark-per-state tests; cost-never-in-PDF test; trial acceptance end to end on real rows (the M4.1 fixtures replaced by the API).
- API tests (real Postgres) and e2e as in scope item 11.
- **Verification note** (in `docs/progress.md`): tests prove the conversion arithmetic, rejections, immutability and the watermark rule as implemented. They do **not** prove that your moisture meter readings are right, that the admixture convention matches your product's datasheet, or that the SYNTHETIC trial criteria suit your plant.

## 8. Rollback / migration

Additive tables and columns; no existing rows change. Rollback = revert the commit; trial-batch fixtures from M4.1 tests stay valid.
