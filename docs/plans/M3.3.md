# M3.3 — Characteristic profiles

Status: **draft, awaiting approval.** No application code is written until this plan is approved.

Features in scope (`06-features.md`): **F-021** Characteristic profiles (tenant / plant / product family). Spec refs: `07-characteristics.md` §3 (profiles, layering, governance), §5, §6 (profile picker, Profiles screen), §7 (roles); `04-phases.md` M3.3 ("CRUD, layering, versions, approval, save as profile, Profiles screen; layering resolution tests; profile version snapshotted on designs").

## 1. Business objective

Let a QC manager write down, once, how the plant makes each product (for example "C30 pump, Aqaba": sand ratio range, SCM range, preferred materials, objective) so that every engineer starts from the approved way instead of from blank rows. A profile never loosens a code limit, is versioned, needs a QC manager's approval before it can drive a trial candidate, and is snapshotted on whatever it produced so later edits change nothing that exists.

## 2. Scope

**In scope**

1. **Schema.** `characteristic_profiles` (identity, scope `tenant | plant | product_family`, `plant_id`, names AR/EN, owner) and `characteristic_profile_versions` (immutable, append-only: version, `applies_to` (strength range, exposure classes, pumpable, placement, season), `characteristics` (Appendix E JSON), material preferences include / exclude / prefer, default objective, default ruleset mode, status `draft | approved`, author, approver, approved_at, change note). `design_requests` gains `profile_versions` (array of `{profileId, version}`), `profile_origins`; `mix_designs.inputs_snapshot` records the profile versions used. Migrations 0016+, integrity triggers (versions append-only, approved versions never change, only the author-or-manager rules below).
2. **Governance (07 §3.3).** QC engineers and QC managers create **draft** versions; a QC manager **approves** (four-eyes: the author may not approve their own version). Editing an approved profile creates the next version as `draft`; the approved one stays in force until the new one is approved. Draft profiles can be used for drafts, evaluations and previews only; **generating trial candidates from a draft profile is blocked** with the reason (F-021 acceptance). New capability `profile.approve` (QC manager); `profile.write` reuses `design.write`.
3. **Check on save (07 §3.3).** Each saved version is checked against ACI and JS for every exposure class in its `applies_to` using the existing loosening check; combinations that would be rejected are listed before approval and **block approval** until fixed (never silently dropped).
4. **Layering (07 §3.2) in the engine.** Pure resolver `resolveProfiles(profiles, request)`: select the approved (or, for previews, latest) profile version of each scope that matches the request (`applies_to` against strength, exposure, pumpable, placement, season; plant scope matches the request plant), layer tenant → plant → product family → request, the more specific layer replaces the less specific one **per characteristic key (and per sub-key for keyed characteristics)**, material preferences merge (exclude wins over include; prefer is additive), default objective/mode from the most specific profile unless the request sets one. Every resolved value keeps its origin (`profile id@version` or `request`). Code and project limits are applied after layering by the existing checker, so a profile can never loosen them.
5. **API.** `GET/POST /api/profiles`, `GET /api/profiles/:id` (with versions), `POST /api/profiles/:id/versions` (new draft version), `POST /api/profiles/:id/versions/:v/approve` (QC manager), `GET /api/profiles/:id/diff?from=&to=`, `POST /api/profiles/match` (which profiles match a request, with the resolved characteristics and origins, plus the loosening check), `GET /api/profiles/:id/usage` ("used by N designs and N requests", and the designs built on older versions). `POST /api/design-requests` accepts `profileIds` (or lets the server select matches), resolves layers, stores `profile_versions` and origins, and **rejects a draft profile for trial generation** with a clear error. Audit on every mutation; cost never involved.
6. **Insight on new version (07 §3.3).** When a version is approved, an info record lists designs built on older versions (no state change). M5.1 owns the insights inbox, so here it is a stored list shown on the profile ("N designs use an older version") and in the API; the inbox item itself arrives with M5.1 (stated in the UI).
7. **Studio.** Profile picker at the top of the Requirements stage: suggests matching profiles, shows "applied from {name} v{n} · {k} overrides", lets the engineer remove a profile or override any value (an override becomes a `request` origin), shows an origin badge on every characteristic row (profile name + version, Request, Code bound), a draft-profile warning that disables Generate (not Evaluate), and **"Save these characteristics as a profile…"** (creates a draft profile/version from the current rows, scope and `applies_to` prefilled from the request).
8. **Profiles screen** (new nav entry after Mix Library, QC roles): list filtered by scope, plant and product family; detail with versions, diff between versions, status chips, approve (QC manager), the loosening-check result per exposure, "used by N designs" with the older-version list; create/edit form reusing the characteristics panel.
9. **Snapshot on designs.** Candidates and designs created from a request carry the profile versions and the per-value origins (shown in the Studio evaluation and in the design detail "Your characteristics" block, which already shows origin).
10. **i18n, tests, docs.** EN/AR strings (Arabic drafts in `docs/i18n-review.md`); engine layering tests (the F-021 three-layer acceptance case, per-key replacement, keyed sub-keys, material preference merge, unmatched `applies_to`, code limits still win); API tests with real Postgres (governance, four-eyes, versions append-only, draft blocked for trial generation, snapshot unchanged after a new version, usage list, plant scope, RBAC); e2e with axe (create → draft → approve → used in Studio with origin badge → save as profile); screens EN/AR × 1440 / 1024 / 390. ADR 0010 (profile versioning and layering).

**Explicitly excluded**

- The insights inbox and Accept flows (M5.1); trials, approval of designs, PDF "Specified characteristics" block (M4.x); product-family master data beyond a free-text family name on the profile; profile import/export; automatic re-generation when a profile changes.

## 3. Assumptions

- A **product family** is a short tenant-defined label on the profile (for example "C30 pump"); matching uses `applies_to`, not the label. The first real families come from Sanad.
- A request matches a profile if every stated `applies_to` field matches (omitted fields match anything). Exposure matches when the request's classes include all of the profile's listed classes.
- Several approved profiles of the same scope can match; the **narrowest** (most `applies_to` fields set, then newest) wins and the others are listed as "also matched"; ties are shown to the user to pick, never guessed.
- Rules are still unverified; a profile that passes the loosening check today is re-checked when rule values change (shown as a stale check on the profile).

## 5. Engineering-correctness risks

| Risk                                       | Mitigation                                                                                                                                                             |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A profile loosens a code limit             | Layering happens before the existing hard-limit checker; the checker runs on the merged result and on save; approval is blocked while any covered exposure is rejected |
| A draft profile drives a trial candidate   | API refuses `profile` generation from a draft version; test; UI disables Generate with the reason                                                                      |
| Edits change designs that already exist    | Versions are immutable rows; requests and designs store `{profileId, version}` and the resolved values; test: edit to v4, design built on v3 unchanged                 |
| Author approves their own profile          | Four-eyes enforced in the API and by a database check; test                                                                                                            |
| Wrong profile silently applied             | Picker always shows what applied, how many overrides, and the origin of every value; ambiguous matches ask the user                                                    |
| A stale "passes the loosening check" label | The check is stored with the rules versions it used; shown stale when rules changed                                                                                    |

## 6. Schema / API / UI impact

- **Schema (0016+):** two tables, new columns on `design_requests`, append-only/immutability triggers, a four-eyes check constraint.
- **API:** endpoints in scope item 5; capability `profile.approve`; OpenAPI entries.
- **Engine:** `profiles/` (types, `matches`, `resolveProfiles`, `mergePreferences`), pure and tested; no change to evaluator or validator arithmetic.
- **UI:** Studio picker and origin badges, Profiles screen, nav entry.

## 7. Verification strategy

- Definition of Done commands; engine coverage stays ≥ 90 %.
- F-021 acceptance as tests: three-layer same-key case (product-family wins, origin shown); v3 → v4 leaves v3-built designs unchanged and lists them; draft profile cannot generate trial candidates.
- Property tests: layering never yields a key that no layer supplied; a request layer always wins; merged result never loosens a limit (the checker rejects, never accepts).
- API tests (real Postgres) and e2e as in scope item 10.
- **Verification note** (in `docs/progress.md`): tests prove layering, governance, immutability and snapshotting as implemented. They do **not** prove any profile's values are good engineering for your plant, or that the synthetic profiles resemble yours.

## 8. Rollback / migration

Additive: new tables, columns and screens. Rollback = revert the commit; stored requests keep their snapshots.
