# M0.2 — Database, auth, RBAC, audit

Status: **draft, awaiting approval.** No application code is written until this plan is approved.

## 1. Business objective

Make every later feature safe to build on: a real PostgreSQL schema foundation, authenticated users, server-enforced roles with plant scoping, an audit trail for every mutation, and the four-eyes guard. Safety contract #9 ("humans approve") and the no-hard-delete rule are enforced here in the data layer, not left to UI discipline.

## 2. Scope

**In scope**

- Drizzle schema + migrations for the foundation tables only: `tenants`, `plants`, `users`, `user_plants`, `sessions`/`accounts`/`verifications` (as Better Auth requires), `suppliers`, `audit_log`, `tenant_settings`.
- Common column conventions applied through shared helpers: `id`, `tenant_id`, `created_at`, `created_by`, `updated_at`, `deleted_at` / `superseded_by` (soft delete / supersede, never hard delete).
- Better Auth (email + password, Drizzle adapter, admin/roles plugin), session cookies, CSRF-safe defaults.
- Roles from `01-domain.md` §10: `admin`, `qc_manager`, `qc_engineer`, `procurement`, `plant_manager`, `sales`, `viewer`. A single typed **permission matrix** (`packages/db` or a small shared module) mapping role → capability, with plant scoping rules (Admin and QC Manager are unscoped; others see only assigned plants).
- Express middleware: `requireAuth`, `requireCapability(cap)`, `requirePlantAccess(plantId)`, request context carrying user, role, tenant, plant ids.
- **Audit log:** every mutating API call writes an `audit_log` row (actor, tenant, entity type/id, action, before/after JSON, request id, timestamp) in the **same transaction** as the change. Append-only: enforced by a DB trigger that rejects `UPDATE`/`DELETE` on `audit_log`.
- **Four-eyes guard:** a reusable `assertNotAuthor(actorId, createdBy)` used by the approval/attestation endpoints (endpoints themselves arrive in M4.1; M0.2 ships the guard, a generic `designs`-free test double, and tests).
- Minimal CRUD endpoints needed to exercise the above: users (admin), plants (admin), user↔plant assignment, tenant settings (admin), plus `GET /me`. These are the "mutations" the audit tests cover.
- `pnpm db:migrate` becomes real; `pnpm db:seed:demo` stays a stub (M1.3) but a small dev seed creates one tenant, one user per role and two plants for tests and local login.
- API test suite against a real Postgres (see §8).

**Explicitly excluded**

- Materials, tests, prices, rules, designs, lifecycle tables (M0.4 – M4.1). Their tables are added by their own milestones' migrations.
- Web login UI, user-management screens, plant switcher (M0.3 and later). M0.2 is API-only.
- Multi-tenant request routing: `tenant_id` columns exist and are set, but v1 runs single-tenant (one row in `tenants`). Tenancy boundary ADR is written now (required before committing to the model).
- SSO/OAuth providers, 2FA, password-reset email delivery (needs an email provider; see Q5).
- e-signature notes UI (M4.1); only the server-side requirement hook exists.

## 3. Assumptions

- PostgreSQL 16+ (sandbox has 16; Docker image in `docker-compose.yml` is 17; CI uses a Postgres service container). No Postgres-17-only features used.
- Exact versions are read from current docs and pinned at install (currently: drizzle-orm 0.45.x, drizzle-kit 0.31.x, better-auth 1.7.x, pg 8.x). I will read each library's docs before use; Context7 is still unavailable, so via web fetch.
- Money columns are `numeric(12,3)`; no money in this milestone.
- Timestamps are `timestamptz` stored in UTC.
- Role is a single value per user (not multi-role) for v1. The matrix in `01-domain.md` §10 has no combined roles.
- "Own plants" for Plant Manager and Procurement-style scoping means plants assigned in `user_plants`.

## 5. Engineering-correctness risks

This milestone has no concrete-engineering logic. The risks are integrity and access control:

| Risk                                              | Mitigation                                                                                                                                                                                                                                    |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A mutation path forgets to audit                  | All writes go through one `withAudit(ctx, fn)` transaction wrapper; a test enumerates every non-GET route and fails if a route lacks the wrapper marker; a DB-level check that audit rows are written in the same transaction (rollback test) |
| Audit rows altered later                          | Trigger raising on `UPDATE`/`DELETE`/`TRUNCATE` of `audit_log`; test attempts each and expects failure; application DB role lacks those privileges where practical                                                                            |
| RBAC drift between UI and server                  | Single permission matrix is the only source; tests generate the full role × capability table and assert both allow and deny for every cell                                                                                                    |
| Plant-scope bypass (IDOR via id guessing)         | Scoping applied in the data layer (query helpers take the request context), not only in route handlers; tests request another plant's resources as each scoped role                                                                           |
| Four-eyes bypass through a second account or race | Guard compares author id on the persisted record inside the same transaction as the transition; test covers author = approver, and author editing after approval request                                                                      |
| Hard delete creeping in                           | No `DELETE` in app code paths; lint rule (`no-restricted-syntax` on `.delete(` for business tables) plus a DB trigger on business tables rejecting deletes; test attempts raw delete                                                          |
| Weak session security                             | Better Auth defaults reviewed: secure/httpOnly/sameSite cookies, secret from `BETTER_AUTH_SECRET` (startup fails if unset in production), rate limiting on sign-in                                                                            |
| Secrets in repo                                   | `.env.example` only; startup config validated with zod                                                                                                                                                                                        |

## 6. Schema / API / UI impact

- **Schema:** the tables in §2, one initial migration plus Better Auth tables (generated with its CLI, reviewed and committed, never edited by hand after).
- **API:** `/api/auth/*` (Better Auth), `GET /me`, `/api/users`, `/api/plants`, `/api/users/:id/plants`, `/api/settings`. OpenAPI generation via zod-to-openapi starts here for these routes so contracts stay single-sourced.
- **UI:** none.

## 7. Package layout

- `packages/db`: Drizzle schema, migrations, `withAudit`, query helpers, permission matrix export (or `packages/rbac` if you prefer a separate package — Q4).
- `apps/api`: auth setup, middleware, routes, config.
- Shared zod schemas for request/response live next to the routes and are the source for OpenAPI.

## 8. Verification strategy

- **Test database:** a real PostgreSQL per test run (no mocks, no in-memory emulation), created from migrations. Locally: `pg_ctl`-started throwaway cluster via a script (the sandbox has no Docker daemon but has Postgres 16 binaries); with Docker available: `docker compose up`. CI: Postgres service container. Each test file runs in its own schema or transaction to stay isolated.
- **RBAC matrix:** generated table-driven tests: every role × every capability × (own plant / other plant / unscoped), asserting 200/403 and no data leakage.
- **Audit:** for each mutating route, assert exactly one audit row with correct actor/before/after; assert no row when the transaction rolls back; assert append-only trigger.
- **Four-eyes:** author ≠ approver tests including plant-scoped edge cases.
- **Soft delete/supersede:** raw `DELETE` on business tables fails; API "delete" sets `deleted_at` and is audited.
- **Auth:** sign-up disabled for public (users created by Admin), sign-in, sign-out, session expiry, unauthenticated 401, cookie flags.
- **Migrations:** `pnpm db:migrate` on an empty database, then re-run (idempotent), plus a check that drizzle-kit reports no schema drift.
- Definition of Done commands all green; API coverage reported (no threshold beyond the milestone's own tests).
- Verification note: tests prove access control, audit completeness and integrity constraints as implemented; they do not prove the role matrix itself is the right business policy — Sanad should confirm the matrix (Q2).

## 9. Rollback / migration strategy

Greenfield data: no production data yet. Migrations are forward-only SQL files committed to the repo; rollback in dev is dropping the database. Better Auth schema changes in later upgrades go through new migrations. Before M0.2 ships to staging (M1.3) a rollback note is added to the runbook.
