# M1.3 — Demo data, legacy import, staging

Status: **draft, awaiting approval.** No application code is written until this plan is approved.

Features in scope (`06-features.md`): **F-009** Legacy mix import with QC attestation. Also delivers the Appendix C demo dataset and the first Railway staging deployment (`04-phases.md` M1.3). Spec refs: `01-domain.md` §2.4–2.5 (designs), §11 (deployment), §13 (legacy import), §14.1 (states); `05-appendices.md` Appendix C, Appendix D; `03-ui.md` (Library, Imports).

## 1. Business objective

Let the pilot plant bring its **existing approved mixes** into Khalta, see which of its own materials each mix uses, and have a QC Manager **attest** the ones that are really approved, so later milestones have a trustworthy baseline. At the same time, give everyone (and the quality gate) a realistic **synthetic demo dataset**, and put the system on a **staging** server so QC and procurement can try it without touching a laptop.

## 2. Scope

**In scope**

1. **Design storage (minimal, forward-compatible):** `mix_designs` (code, name, plant, ruleset mode, version, `status` per §14.1, `approval_source` `khalta` | `legacy_attested`, external approval reference, approved by/at, import batch, `inputs_snapshot`, requirements as imported), `mix_design_lines` (material, kg/m³ SSD as imported, original unit and quantity, optional L/m³), `design_transitions` (append-only, who/when/evidence), `production_volumes` (design, plant, month, m³). Statuses beyond those M1.3 uses exist in the enum but their transitions arrive with M2.1/M4.1. Designs are never hard-deleted; edits create versions.
2. **Legacy import (F-009)** from `.csv` / `.xlsx` in the Appendix D long format (`templates/legacy-mix-designs.csv` created, EN and AR header aliases accepted):
   - **Column mapping** step (auto-detected, user can correct) → **material matching** step → **validation preview** → all-or-nothing **commit** (same pattern as the rules and price imports: preview stored immutably, stale-preview check).
   - **Material matching, Arabic first:** names are normalized (diacritics, tatweel, alef/ya/ta-marbuta variants, Arabic-Indic digits, spacing, case) and matched against the library's Arabic and English market names. **Only an exact normalized match is pre-selected**; near matches are **suggestions the user must confirm** (ordered by similarity, the similarity itself is not presented as a probability). Unmatched names can be mapped to an existing material, left unresolved, or created as a new material (empty tests) from the same screen. Category from the file must agree with the chosen material or it is an error.
   - **Checks at preview** (none needs code rules): known plant, numeric positive quantities, unit `kg/m3` or `L/m3` (`L/m3` converts to kg only through the material's SG; missing SG is a named error, not a guess), one line per material per design, strength basis and test age recognized, exposure classes recognized (`F0–F3`, `S0–S3`, `W0–W2`, `C0–C2`), duplicate `design_code` within the file or already in the library, every design has at least one cement line and water. Warnings (not errors) for: materials with no tests (cannot be evaluated), declared-only key properties, material not priced at that plant.
   - Imported designs are created as **`draft` with an "evaluation pending" flag** (see Q1: the evaluator arrives in M2.1; a design cannot honestly be `evaluated` before an evaluation exists).
3. **Attestation queue (Library screen):** list of imported designs and their data-quality warnings; a **QC Manager** (`design.attest`) opens a design, enters the **external approval reference** (required, from the file if present), an optional approval date, whether it is **currently in production** (and at which plant), and a typed **e-signature note**. Result: status `approved`, `approval_source: legacy_attested`, optionally `in_production`; transition recorded append-only; audit entry. **Four-eyes:** the person who imported the file cannot attest it (a second QC Manager is needed; see Q2). Attestation says "this mix was approved outside Khalta", **never** "Khalta checked it"; the UI labels such designs "Legacy attested · not yet evaluated by Khalta" until M2.1 evaluates them.
4. **Library screen (read side):** designs list (code, name, plant, status chip, approval source chip, evaluation-pending chip, volume), detail sheet (lines with original units, source file row, warnings, transitions history). Compute-free: no compliance, cost or strength figures appear before M2.1 (no number is shown that Khalta has not calculated and verified).
5. **Demo dataset generator** (`packages/db/seeds/demo/generate.ts`, fixed seed, deterministic, every record labelled **SYNTHETIC**), for what exists by M1.3: 2 plants; 3 cements (one with `c3a_pct`) + 1 natural pozzolan; 6 aggregates per plant with the Jordanian market names and full tests (one expired); 2 admixtures with 4-point dosage tables; full price matrix (different per plant, one stale cell, one material unpriced at AQB-01) and two price snapshots; **3 legacy designs per plant** (two attested, one awaiting attestation; attested ones created through the same service code path, by two different QC Managers) with 6 months of synthetic volumes. Strength results and designs in later lifecycle states are added by the milestones that introduce those tables (M4.x); the generator is structured so they plug in. Runs via `pnpm db:seed:demo`, refuses to run in production, idempotent.
6. **Staging deployment (Railway):** production-grade `Dockerfile` for the API (multi-stage, non-root, migrations then start, `/health`), the built web app **served by the API from the same origin** (no CORS, session cookies stay first-party; see Q3), `railway.json`, environment-variable contract (`DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `APP_BASE_URL`), first-admin bootstrap, a `docs/runbooks/staging.md`, and a CI-friendly smoke script (`pnpm smoke:staging <url>`: `/health`, sign-in page, authenticated `/api/me`). The deploy itself uses the Railway tools **only after your go-ahead** (Q4).
7. **RBAC:** reuses `import.run` (Admin, QC Manager) and `design.attest` (QC Manager); adds `library.read` visibility only (exists). No new capabilities.
8. **Docs:** `docs/runbooks/staging.md`, README update, ADR 0006 (static web served by the API on staging).

**Explicitly excluded**

- Running the evaluator, compliance tables, cost per m³, strength adequacy and the "evaluated" state (M2.1/M2.2); cost baselines (M2.2).
- Strength results, trial batches, PDFs, savings ledger, and designs in other lifecycle states (their milestones).
- Fuzzy matching of materials **inside** requests, profile layering (M3.x), ERP integration (M6.1).
- Production environment, backups and restore drill (M6.2); staging has a managed database but no backup promise.
- Exporting a design as a fixture (M2.2).

## 3. Assumptions

- Appendix D column names are authoritative; header aliases (EN/AR) follow the same approach as the price import. Multiple designs per file; a design's header fields repeat on each line (taken from the first line, conflicts between lines of the same design are an error).
- Quantities are **per m³ SSD** as stated in Appendix D; the importer does not correct for moisture.
- Matching never changes the library silently: new materials are created only by an explicit action, are `user_declared`-empty (no tests) and are flagged "created during import".
- `approval_reference` in the file pre-fills the attestation form but is not itself an attestation.
- Demo "expired test" uses a **synthetic, demo-only, unverified** test-age limit written to the demo tenant's `eng.test_age_limit_days.*` and `stalePriceDays` setting (the real seeds stay null); the demo database is labelled SYNTHETIC in the UI footer when `KHALTA_DEMO=1`.
- Railway: one project with `staging` environment, services `api` (serving web) and a managed PostgreSQL; the domain spec's separate `web` and `worker` services are deferred (static-from-API now; worker with pg-boss in M5.1).
- Docker is available locally for a build check only if a daemon runs; otherwise the Dockerfile is validated by a CI-style dry run (`docker build` is run in the first staging deploy and any failure is fixed before the milestone is closed).

## 5. Engineering-correctness risks

| Risk                                                                                  | Mitigation                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A near-match silently links a legacy line to the wrong material (e.g. فولية vs حمصية) | Only exact normalized matches are pre-selected; every other link needs a click; the preview lists each link with its method (exact / confirmed by user / created); tests with near-name pairs                 |
| Wrong quantity unit or litre/kg confusion corrupts a baseline                         | `L/m3` converts only with a known SG, otherwise error; original unit and quantity stored next to the converted kg; round-trip test (export back equals file)                                                  |
| An imported design looks approved or compliant without anyone attesting/evaluating    | Imported = `draft` + "evaluation pending"; no compliance/cost figures shown; attestation is a separate signed human action; labels "Legacy attested · not yet evaluated"                                      |
| Self-attestation of one's own import                                                  | Four-eyes (author ≠ attester) enforced on the server and in tests; the import's `created_by` is the author                                                                                                    |
| Duplicate import creates two copies of a design                                       | `design_code` unique per tenant (live rows); preview flags duplicates in the file and in the library; commit is all-or-nothing and the preview is single-use                                                  |
| Import file with formulas/macros or huge size                                         | Values only (formula results), 5 MB cap, 5,000 lines, type by signature, no macro execution                                                                                                                   |
| Demo data mistaken for real                                                           | SYNTHETIC label in every name/note, banner when `KHALTA_DEMO=1`, seeder refuses production and non-demo databases, tests assert the label on every generated record                                           |
| Demo generator not deterministic                                                      | Seeded PRNG; a test generates twice and compares a content hash                                                                                                                                               |
| Staging secrets leak or dev seed runs on staging                                      | Secrets only in Railway variables, `BETTER_AUTH_SECRET` generated, never committed or logged (redaction test exists); `seed:dev` still refuses production-like `NODE_ENV`; demo seeding needs `KHALTA_DEMO=1` |
| Migration failure at deploy takes the service down                                    | Migrations run before start in a transaction-per-file; failure aborts the deploy; rollback = previous image (additive migrations only)                                                                        |
| Cookies/CORS misconfiguration on staging                                              | Same-origin serving; `BETTER_AUTH_URL`/`APP_BASE_URL` set to the staging origin; smoke script signs in and calls `/api/me`                                                                                    |

## 6. Schema / API / UI impact

- **Schema (migration 0008+):** `mix_designs`, `mix_design_lines`, `design_transitions` (append-only), `production_volumes`, `legacy_import_batches` (immutable preview rows, status). Triggers: no hard delete, transitions append-only, a design's imported inputs immutable (changes = new version), `approved` legacy-attested requires approval reference and approver (check constraint).
- **API:** `POST /api/imports/legacy/preview` (upload), `POST /api/imports/legacy/commit`, `GET /api/imports/legacy/:id`; `GET /api/designs` (+ filters), `GET /api/designs/:id`, `POST /api/designs/:id/attest`, `GET /api/designs/attestation-queue`; static web hosting and `/health` readiness incl. DB.
- **Engine (pure):** Arabic/English name normalization and similarity ranking, legacy-row parsing and validation, unit conversion (reuses decimal helpers).
- **UI:** Imports screen (legacy import wizard: upload → mapping → matching → preview → commit), Library screen (list, detail, attestation queue, attest dialog), demo banner. Nav "Library" and "Imports" become real.
- **Ops:** `Dockerfile`, `.dockerignore`, `railway.json`, `docs/runbooks/staging.md`, `pnpm smoke:staging`, `pnpm db:seed:demo`, ADR 0006.

## 7. Verification strategy

- Definition of Done commands green; zero serious axe violations; `pnpm screens` AR/EN × 1440/1024/390 reviewed (no figure the system did not compute; SYNTHETIC visible; Arabic matching UI correct in RTL).
- **Engine tests:** normalization (variants, tatweel, diacritics, digits), similarity ranking and the "exact only is pre-selected" rule (including near-name traps), legacy row parsing/validation (every error and warning), litre→kg conversion with and without SG; property tests (normalization idempotent; normalization never merges distinct exact names).
- **API tests (real Postgres):** import preview/commit all-or-nothing, stale-preview and single-use, duplicate codes, unit/SG errors, matching decisions persisted, **round trip** (export the created designs back to the long format and compare with the source file), attestation (reference required, four-eyes, e-signature, transitions append-only, in-production release), RBAC matrix extension, plant scoping (404), audit rows, database-level immutability, demo generator determinism and SYNTHETIC labelling, demo idempotency.
- **E2E:** import wizard with an Arabic file (exact, near and unmatched names), attest as a second QC Manager, self-attest refused, library list/detail in EN/AR, demo banner; staging smoke script against a locally started production build of the container image (`docker build` + `docker run` when a daemon is available, else the same `node` entrypoint).
- **Staging:** after your go-ahead: deploy, run the smoke script against the Railway URL, record the URL and results in `docs/progress.md`.
- **Verification note:** tests prove parsing, matching rules, conversions, state changes and deployment mechanics as implemented. They do **not** prove the legacy designs are correct or compliant, that a matched material is the physical material the plant uses, or that the demo numbers resemble real production.

## 8. Rollback / migration

Additive migrations; the importer creates only designs, lines and a batch row. Rollback = revert the commits and drop the new tables on dev databases; a staging deploy rolls back by redeploying the previous Railway image. No production data exists yet.
