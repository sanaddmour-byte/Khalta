# M6.1 — Integration: approved-design and batch-weight CSV exchange

Status: **approved with the default answers; built (2026-10-03).**

Feature in scope (`06-features.md`): **F-029** CSV export for batch plants / ERP. Spec refs: `04-phases.md` M6.1 ("Approved-design/batch-weight CSV exchange first; REST/OpenAPI ERP integration only after field mapping and pilot sign-off. Done: CSV contract tests; API contract tests once the integration ADR is approved"); `01-domain.md` §1 item 3 ("integrate with ERP/batching only after measured savings and QC governance are proven"), §6 (batch weights), §14.1 (lifecycle); `05-appendices.md` Appendix D (CSV templates).

## 1. Business objective

Get what the plant is allowed to produce out of Khalta and into the batching system without retyping, and do it so a plant can never receive a design that is not approved. A batch plant or an ERP gets two files: the **approved designs** (proportions per m³) and the **batch weights** of a saved production correction (what to actually weigh, with the day's moisture and the independent check's verdict). The format is a documented, versioned contract that a plant's IT person can parse without asking us. Nothing flows back in this milestone, and nothing is called over the network.

## 2. Scope

**In scope**

1. **Approved-designs CSV** (`GET /api/exports/designs.csv`). One row per material line of every design that is `approved` or `in_production` at the plants the user may see (optionally one plant or one design). Draft, evaluated, trial, retired, superseded and suspended designs are **never** exported; a suspended design disappears from the next export on purpose. Columns follow Appendix D (`design_code, plant_code, design_name, fc_mpa, strength_basis, test_age_days, exposure_classes, slump_mm, nmas_mm, pumpable, material_name, material_category, quantity, unit`) plus: `schema`, `version`, `status`, `approved_at`, `approved_by`, `design_hash` (the same version hash the e-signature binds to), `ruleset_mode`, `material_id`, `line_no`, `quantity_basis` (`kg/m3 SSD`). **Never any cost, price, margin or saving.**
2. **Batch-weights CSV** (`GET /api/batch-instances/:id/weights.csv`, and a plant/date range variant). One row per material line of a saved **batch instance** (M4.2): SSD mass, oven-dry mass, wet batch weight, free water, the total and absorption moisture used, admixture solution water, water to add, per m³; plus the batch's header values (design code and version, plant, kind, created at and by, the moisture reading date, the **independent check verdict**, and the instance id). Only instances whose independent check passed exist (the database already enforces that), and only for designs that are still approved or in production at export time; otherwise the export is refused with the reason.
3. **The contract** (`docs/contracts/csv-exchange.md`, versioned `khalta.designs.v1` and `khalta.batch-weights.v1`): UTF-8 with a byte-order mark (so Excel reads Arabic), comma delimiter, CRLF line ends, RFC 4180 quoting, `.` decimal point, no thousands separators, ISO dates and UTC timestamps, quantities with the stored precision, the **exact header row frozen** (a changed header is a version bump, enforced by a test). Text cells that start with `=`, `+`, `-` or `@` are neutralised (spreadsheet formula injection) without altering numbers. Semicolon-separated lists for exposure classes (as in the import template).
4. **Round trip.** The designs export is accepted by the existing legacy-import parser for the shared columns (a test), so a plant can move designs between Khalta instances, while the importer still treats them as **legacy, unattested** (an export is not an attestation).
5. **Integrity and audit.** Every export is audited (who, which plants and designs, row count, SHA-256 of the file) and returns the hash in a header (`X-Khalta-Sha256`) and in the file name stem, so the plant can prove which file it loaded. Exports are read-only: no state changes.
6. **Access.** A new capability **`export.csv`** for QC manager, QC engineer and plant manager (plant-scoped as everywhere); admin, procurement, sales and viewers have none. Cost-blindness is structural (the columns do not exist).
7. **UI.** On the Library: "Export approved designs (CSV)" (current plant or all the user can see). On a design's **Batch weights** history (M4.2): "Download CSV" per saved instance. Download names show the plant, date and hash stem. EN/AR strings; a short on-screen note that the file is a copy for the batching system, not an approval.
8. **REST / ERP integration: not built.** A short **proposed** ADR (`docs/adr/0016-erp-integration-proposed.md`) lists the open questions (field mapping, direction, identity, idempotency, acknowledgements, who signs the pilot) and the contract tests that would follow; it stays `proposed` until you approve it after the field mapping.
9. **Tests, docs.** CSV contract tests (frozen headers, encoding and BOM, quoting of commas, quotes, line breaks and Arabic, formula-injection neutralisation, decimals, ordering, hash equals the file); an **independent reference parser** in the test that rebuilds each design from the CSV and compares it with the database; property tests (any approved design set round-trips; the file is identical across two runs; no row for a non-approved design, ever; no cost field in any export); API tests with real Postgres (RBAC and plant scope per role, suspended and superseded designs vanish, batch weights match the stored instance exactly, refusal for a design no longer live, audit entries and hash); e2e with axe; screens EN/AR × 1440 / 1024 / 390; ADR 0015 (CSV contract) and 0016 (proposed).

**Explicitly excluded**

- Any REST or push integration, webhooks, SFTP or scheduled delivery; reading anything back from an ERP or batching system (produced volumes, actual weights); price or cost export; XLSX; PDF (the M4.2 submittal already exists); any change to a design, rule or price.

## 3. Assumptions

- A batch instance stores per-m³ weights (the M4.2 conversion); the batching system scales to its batch size. The file says so (`basis` column), and nothing in it is a batch-size calculation.
- One file per request; no pagination (a tenant's approved designs are in the hundreds).
- Material names are the plant's market names as stored (Arabic accepted); `material_id` is the stable key for a system that matches by id.

## 5. Engineering-correctness risks

| Risk                                                         | Mitigation                                                                                                                                            |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| A non-approved design reaches a plant                        | The query selects only `approved` / `in_production`; a property test over every lifecycle state; batch weights refuse a design that left those states |
| Numbers altered on the way (rounding, locale, spreadsheet)   | Decimal strings straight from the stored values, no float formatting; `.` decimal; the reference parser compares exactly                              |
| Spreadsheet formula injection from a material or design name | Neutralise leading `= + - @` (and tab/CR) in text cells; tested with hostile names                                                                    |
| Cost or price leaks into a file for a plant                  | No cost columns exist; a test scans every export for cost-like fields; the capability excludes cost-blind roles                                       |
| A plant loads a stale or altered file                        | `design_hash` binds each row to the approved version; the file SHA-256 is audited and returned                                                        |
| The contract drifts silently                                 | Frozen header and a version column; a changed header fails a test                                                                                     |
| Plant isolation                                              | Plant scope on every query; tests for scoped and unscoped roles                                                                                       |

## 6. Schema / API / UI impact

- **Schema:** none (exports read existing tables; the audit log records each export).
- **RBAC:** one capability `export.csv` (rbac matrix and its tests updated).
- **API:** `GET /api/exports/designs.csv`, `GET /api/batch-instances/:id/weights.csv`, `GET /api/exports/batch-weights.csv?plantId&from&to` (audited reads).
- **Engine:** pure `exchange/` module (CSV writer with the escaping rules, row builders, the frozen headers), no I/O.
- **UI:** Library export button; Batch weights history download.

## 7. Verification strategy

- Definition of Done commands; engine coverage ≥ 90 %.
- **Phase gate as tests:** the CSV contract tests above pass (frozen headers, independent reference parser, never a non-approved design, never cost). The REST contract tests wait for an approved ADR (not part of this milestone).
- **Verification note** (in `docs/progress.md`): tests prove the files match the database exactly, follow the documented contract, exclude every non-approved design and every cost figure, and are audited. They do **not** prove that your batching system reads them: that needs your field mapping and a pilot.

## 8. Rollback / migration

Read-only additions: new routes, one capability, a UI button. Rollback = revert the commit; nothing stored changes.

## 9. Questions for you (default in brackets)

1. **Format:** UTF-8 with BOM, comma delimiter, `.` decimal [yes]; or semicolon-delimited for Arabic-locale Excel [no].
