# M2.2 — Mix intelligence pilot

Status: **draft, awaiting approval.** No application code is written until this plan is approved.

Features in scope (`06-features.md`): **F-012** Bilingual compliance table with clause references; **F-013** Cost baseline and theoretical opportunities. Per `04-phases.md` M2.2 also: manual editor, legacy portfolio evaluation, attestation flow (exists since M1.3), cost baselines with price snapshots, data-quality blockers, theoretical entries in the ledger. Spec refs: `01-domain.md` §1.1, §2.7, §14.2; `02-codes.md` §8; `03-ui.md` §4D; `07-characteristics.md` §4.5.

## 1. Business objective

Turn the M2.1 evaluator into the first thing a QC manager and a plant manager can use on the whole portfolio: see every imported design's compliance, cost and data gaps on one page, fix a design by hand in a controlled way, and record **what the portfolio costs today** (the baseline) so that any later saving is measured against a fixed, honest reference. Nothing here claims a saving is real: opportunities are **theoretical** and say so.

## 2. Scope

**In scope**

1. **Bilingual compliance table (F-012)**, replacing the functional M2.1 list: failures first; filters by result, code (ACI / JS / PROJECT) and requirement class; every row shows the value, limit, governing source, clause (linking to the Rules screen), class, evidence chips, the blocker for "not evaluated" rows and a **traceability popover** (formula, named inputs, rule key, versions from the trace). Engine explanations (blockers, assumptions, data-quality details) become **structured codes with parameters** (e.g. `{code:'c3a_missing', material}`) so the Arabic text is a translation, not English leaking through; the English text stays in the report for audit. Compliance and "Your characteristics" stay separate blocks.
2. **Manual editor**: edit a design's proportions and requirements as a **new draft version** (never in place: inputs of a stored version stay immutable). A change returns the design to `draft` (lifecycle edge `evaluated → draft` turns on), shows a live preview (the evaluator runs in the browser on the same snapshot builder output; the server re-runs evaluator and validator on save), and every proportion change on an approved/in-production design needs a trial (minor-adjustment policy is "none"), so editing an approved design creates version N+1 as `draft` and leaves N untouched. Version history and a line-by-line diff between versions.
3. **Portfolio evaluation**: evaluate all designs (selected plant or all) in one audited batch; a **portfolio table** (Library page, "Portfolio" tab) with verdict, validator status, cost per m³ (cost-visible roles), data-quality blockers count, evidence chips, stale-input flag; sortable, filter by "failing", "incomplete", "needs revalidation", "inputs changed". Exports (CSV) for roles with `export.priceCost`.
4. **Data-quality blockers view**: one list of every material/test/price/rule gap that stops a design from being evaluated or from being trusted, grouped by cause with the designs it affects (so one new lab test unblocks many designs).
5. **Cost baseline and price snapshots (F-013)**: a **baseline** = one named, immutable record of (design, version, plant, price snapshot, cost per m³, evaluation id, eligible volume per month from the import, period). Created for attested designs from a chosen price snapshot (existing M1.2 snapshots), never silently re-priced. Baseline cost uses the **same snapshot** for any later comparison (§14.2). Annualized baseline spend = cost × eligible volume × 12, labelled as an estimate from the volumes in the file.
6. **Theoretical opportunities and ledger entries**: with no optimizer yet, an opportunity is a **manual variant**: a draft version of a baseline design that evaluates compliant, validated, and cheaper **at the baseline's own snapshot**. The ledger entry stores baseline and proposed versions, both price snapshots (the same one), per-m³ difference, eligible volume, period, status `theoretical`, reason code. It is labelled "theoretical: not approved, not realized", never summed with other states, and creating one does not approve anything (a trial is still required, M4.x).
7. **ADR 0008: savings baseline** (what a baseline is, why snapshots, why theoretical stays separate), required by `04-phases.md`.
8. Tests, e2e (import → evaluate → attest → baseline → manual variant → theoretical entry), axe, screens EN/AR × 1440/1024/390.

**Explicitly excluded**

- The optimizer and generated candidates (M3.x); approved and realized savings states, insights, the Savings dashboard (M5.1); trials and approval (M4.x); PDF (M4.2); strength results (M4.2).
- Any claim that a theoretical entry is a saving; any aggregation across states.

## 3. Assumptions

- All 79 not-on-file rule values and the unverified ACI values stay as they are: every comparison is provisional; a variant that "passes" while rules are unverified is shown as provisional, and the opportunity says so.
- Volumes come from the legacy file (`avg_monthly_volume_m3`, a stated average, not production records); annualization is a labelled estimate. Real volumes arrive with M5.1.
- A manual variant is only an opportunity if it is **compliant on every evaluated check, has no "not evaluated" hard check, and the validator passed** at the baseline's snapshot; otherwise it is saved as a draft but not offered as an opportunity (reason shown).
- Evidence for editing: any user with `design.write` may create a draft version; nothing a draft contains is approved or in production.

## 5. Engineering-correctness risks

| Risk                                                          | Mitigation                                                                                                                                                   |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A cheaper variant is shown as a saving because prices moved   | Both costs computed at the **same stored snapshot**; the ledger stores that snapshot id; test: changing live prices cannot change an entry                   |
| An edited approved design silently changes production         | Edits only create version N+1 as `draft`; N immutable (database trigger exists); lifecycle refuses any other path; test per state                            |
| Browser preview differs from server result                    | The browser runs the same pure evaluator; the server recomputes and the validator checks; the saved report is the server's; a test compares both on fixtures |
| Opportunity from a failing, incomplete or unvalidated variant | Eligibility is computed from the stored evaluation (all hard checks pass, none not evaluated, validator pass); property test over generated variants         |
| Savings summed across states or designs                       | Only `theoretical` exists; per-entry display; no totals row across entries of different baselines/snapshots; UI test                                         |
| Arabic text drifts from English meaning                       | Structured reason codes + parameters, one translation table, parity test that every code has both languages                                                  |
| Annualized spend over-trusted                                 | Always labelled "estimate from file volumes"; volumes shown beside it                                                                                        |
| Cost leak to cost-blind roles                                 | Portfolio, baseline and ledger endpoints strip cost server-side; per-role tests                                                                              |

## 6. Schema / API / UI impact

- **Schema (migrations 0012+):** `mix_designs.parent_design_id` already exists (version chain); `cost_baselines` (immutable: design, version, plant, price snapshot id, evaluation id, cost per m³ numeric, monthly volume, period, created_by/at), `savings_entries` (immutable ledger rows: baseline id, proposed design/evaluation, snapshot id, per-m³ difference numeric, eligible volume, period, state `theoretical`, reason code); both append-only by trigger, no hard delete.
- **API:** `POST /api/designs/:id/versions` (new draft version from edits), `GET /api/designs/:id/versions`, `POST /api/designs/evaluate-batch`, `GET /api/portfolio`, `GET /api/data-quality`, `POST /api/baselines`, `GET /api/baselines`, `POST /api/savings/theoretical`, `GET /api/savings` (theoretical only), CSV export; engine gains structured reason codes in the report (additive, `schema` stays compatible; evaluator/validator versions bump).
- **UI:** compliance table component (filters, popovers), editor (proportions grid with live preview, diff), Portfolio tab, Data-quality screen, Baselines and Opportunities sections (in the Savings screen placeholder, cost-visible roles).
- **RBAC:** `design.write` (edit, batch), `library.read` (portfolio, baselines read), `cost.view` (cost fields), `export.priceCost` (CSV); a new capability `baseline.create` for QC manager only (proposed in the manifest if you prefer a different role).

## 7. Verification strategy

- Definition of Done commands; zero serious axe violations; `pnpm screens` AR/EN × 1440/1024/390 reviewed (failures first, no pass without evidence, units isolated in RTL, popovers readable, theoretical labels everywhere).
- Unit/property tests: reason-code completeness (every blocker/assumption/quality code has EN + AR), eligibility rules, snapshot-stability of ledger entries, version immutability, diff correctness, preview = server on fixtures, batch evaluation determinism and 200-design performance.
- API tests (real Postgres): version creation per lifecycle state, illegal edits rejected, baseline immutability (database level), snapshot basis honoured, opportunity eligibility, cost stripping, RBAC, plant scope, audit rows.
- E2E: import → evaluate → attest → baseline → manual variant → theoretical entry; Arabic walkthrough with axe.
- **Verification note** in `docs/progress.md`: tests prove baselines are fixed to their snapshot, variants never overwrite approved designs, and only validated compliant variants become opportunities. They do **not** prove any saving is achievable in production, that volumes are real, or that a variant is acceptable to produce.

## 8. Rollback / migration

Additive migrations (two tables, no changes to existing data). Rollback = revert commits and drop the tables on dev databases; baselines and ledger entries are derived records and can be recreated from stored evaluations and snapshots.
