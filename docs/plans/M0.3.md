# M0.3 — Design system and app shell

Status: **approved and implemented (2026-10-01).**

## 1. Business objective

Give every later screen one consistent, bilingual, accessible foundation: design tokens (light/dark), a small set of wrapped components, an RTL-correct app shell with role-aware navigation, a plant switcher and a command palette. QC engineers and plant managers will use this daily in Arabic on laptops and tablets, so Arabic and RTL are first-class from the first screen, not retrofitted.

## 2. Scope

**In scope**

- **Tokens** (`packages/ui`): the palette in `03-ui.md` §5 as CSS variables on `:root` with a dark override, exposed to Tailwind v4 via `@theme`; typography (IBM Plex Sans Arabic / Sans / Mono, self-hosted via Fontsource), spacing, radius, motion (≤ 150 ms), density (comfortable/compact).
- **Wrapped components** (`packages/ui`, built on Radix primitives, Tailwind v4, logical utilities only): Button, IconButton, Input, Label, Checkbox, Switch, Select, Tabs, Dialog, Popover, Tooltip, DropdownMenu, Separator, Card, Skeleton, Table primitives, Toaster (sonner), CommandPalette (cmdk), `Bdi`/`Ltr` wrapper for mixed-direction tokens (units, classes, codes, clause refs), and the domain chips: `StatusChip` (pass / warn / fail with icon + text + colour), `CodeBadge` (ACI / JS / PROJECT), `EvidenceChip` (all nine evidence statuses from CLAUDE.md), `SavingState` label (theoretical / approved / realized). Chips are visual only in M0.3; nothing computes an evidence status yet.
- **i18n** (`apps/web` + `packages/ui`): i18next + react-i18next + ICU; `en` and `ar` resource files; language toggle (ع / EN) setting `<html lang dir>` and the Radix `DirectionProvider`; Western digits by default via `Intl.NumberFormat('ar-JO-u-nu-latn')`, Arabic-Indic honoured from the tenant `numberFormat` setting; dates via date-fns with Arabic locale, displayed in Asia/Amman. `packages/ui/glossary.json` seeded with the terms in `03-ui.md` §6 and a test that every glossary term used in the UI resolves from it.
- **App shell** (`apps/web`): Vite + React 19 + TanStack Router (code-based routes) + TanStack Query; side navigation at the start edge (right in Arabic) with all eleven sections from `03-ui.md` §3; top bar with plant switcher, command palette trigger, language toggle, theme toggle, notifications placeholder and user menu. Navigation is **role-aware**: an item appears only if the user's capabilities (from `@khalta/rbac`, delivered by `/api/me`) allow it; absent, not disabled.
- **Sign-in screen and session handling:** minimal login page against the existing Better Auth sign-in endpoint, sign-out, redirect guards, `/api/me` + `/api/plants` through TanStack Query so the plant switcher and role-aware nav are real (needed for an honest quality gate). No user-management UI.
- **Section placeholder pages:** each of the eleven sections renders an empty-state card (title, one-line description of what arrives and in which milestone) so navigation, active state and RTL mirroring can be verified. Empty states follow the "teach, don't blank" principle.
- **`/dev/components`:** every `packages/ui` component in LTR and RTL, light and dark, visible only in development and in screenshot runs.
- **Lint and tests hardening:** the three M0.1 lint rules now run on real UI code. Where Radix/shadcn patterns use physical utilities (`left-*`, `slide-in-from-left`, `data-[side=right]`) they are rewritten to logical equivalents.
- **Quality gate** (`03-ui.md` §8): `pnpm screens` produces AR + EN × 1440/1024/390 px for shell, dev/components and sign-in into `docs/screens/M0.3/`; every screenshot is reviewed against the checklist, defects fixed, and the review recorded in `docs/progress.md`.

**Explicitly excluded**

- Any domain screen (Studio, Library, Prices, Rules, …), charts (ECharts), the spreadsheet grid (ADR in M1.2), forms beyond sign-in, user/plant admin screens, notification content, insights.
- Offline-safe tablet entry (arrives with Materials, M1.1).
- Server-rendered HTML for PDFs (M4.2), though tokens are written so the same CSS can be reused there.
- Cost visibility rules in UI beyond the nav gating (no cost figures exist yet).

## 3. Assumptions

- Versions are read from the registry and pinned at install: Tailwind 4.3, @tailwindcss/vite 4.3, radix-ui 1.6, cmdk 1.1, sonner 2.0, lucide-react, i18next 26, react-i18next 17, i18next-icu 2.4, TanStack Router 1.170 / Query 5.104, Fontsource IBM Plex 5.3, jsdom + Testing Library for component tests. I will skim each library's own README/types before first use (the docs sites of some libraries were not reachable in this sandbox in M0.2).
- shadcn/ui is used as a **pattern**, not via its CLI: components are written by hand against Radix in `packages/ui` so we control logical-CSS correctness and avoid registry network dependency.
- Local `pnpm dev` runs the Vite dev server with `/api` proxied to the API on port 3000, so session cookies are same-origin (no CORS). Production hosting of the web build (static service behind the same origin or a proxy) is decided in M1.3 with the Railway deploy.
- Screens and e2e run against a real API + the local test Postgres with the `seed:dev` users (one per role). The synthetic demo dataset (Appendix C) does not exist until M1.3, so M0.3 screenshots show the shell with real users and plants but placeholder section content.
- Brand: text wordmark "خلطة · Khalta" in IBM Plex until a logo exists.
- Arabic UI strings are drafted by me; the technical glossary terms come from the spec. A native-speaking QC reviewer should confirm wording (see Q4).

## 5. Engineering-correctness risks

No concrete-engineering logic here. The risks are about presenting information correctly:

| Risk                                                                                              | Mitigation                                                                                                                                                         |
| ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Numbers, codes or units mirrored or reordered in RTL (e.g. `C30/37`, `kg/m³`, `CEM II/A-P 42.5N`) | `Bdi`/`Ltr` wrapper component and tests that render each token inside an RTL container and assert `dir="ltr"` isolation; screenshots reviewed for mirrored numbers |
| Status relying on colour alone, or brand green mistaken for "pass"                                | `StatusChip` always renders icon + text + colour; brand green is never used for status; contrast test (below)                                                      |
| Insufficient contrast in either theme                                                             | A unit test parses the token CSS and asserts ≥ 4.5:1 for every text/background pair listed in `03-ui.md` §5 in light and dark                                      |
| Hard-coded or physically directional UI slipping through                                          | ESLint rules from M0.1 now enforced on real code; Playwright test asserts that nav, drawers and popovers appear on the correct side in both directions             |
| Evidence/saving chips misused later as scores                                                     | Chips are label-only components with a closed set of enumerated values (type-checked); no numeric prop                                                             |
| Wrong direction on portals (dialogs, popovers, toasts rendered outside the root)                  | `DirectionProvider` plus `dir` set on `<html>`; e2e checks a dialog and a dropdown in RTL                                                                          |
| Arabic text clipped or mis-shaped (line-height, font fallback)                                    | Self-hosted Plex Sans Arabic, Arabic line-height 1.7, no uppercase/letter-spacing on Arabic; screenshot review                                                     |
| Role-aware nav diverging from the server's capabilities                                           | Nav visibility is derived from the same `@khalta/rbac` capabilities returned by `/api/me`; test asserts the visible nav items for each role                        |

## 7. Verification strategy

- Definition of Done commands all green (`typecheck`, `lint`, `test`, `test:rules`, `e2e`), zero serious axe violations.
- **Unit/component tests** (Vitest + Testing Library + jsdom): token contrast, chips (closed value sets, icon+text), `Bdi`, number/date formatting in both locales (Western digits default, Arabic-Indic opt-in, Asia/Amman), glossary coverage, nav visibility per role, language/theme persistence.
- **E2E** (Playwright): sign in as each seeded role, navigate every section, toggle language (assert `dir`, `lang`, nav side, a dialog, a dropdown and the palette in RTL), toggle theme, `Ctrl/Cmd+K` palette, plant switcher scoping (a scoped user sees only their plants), sign out; axe on shell, sign-in and `/dev/components` in EN/AR × light/dark.
- **Screens:** `pnpm screens` AR/EN × 1440/1024/390; I review them against the §8 checklist (mirrored numbers/codes/charts, clipped Arabic, physical CSS, focus states, empty/loading/error states, units on numbers, no hard-rule levers, saving-state labels) and list findings and fixes in `docs/progress.md`. Where I cannot judge Arabic typography with certainty from screenshots, I will say so.
- Verification note: tests prove the shell renders and behaves correctly in both directions and meets the automated accessibility and contrast checks. They do not prove the Arabic copy is idiomatic or that the layout suits real plant-floor devices; both need Sanad's review.
