# M3.2 — Trial recommendation UX (Design Studio)

Status: **draft, awaiting approval.** No application code is written until this plan is approved.

Features in scope (`06-features.md`): **F-018** Four-stage Design Studio with Evaluate / Generate paths, **F-019** Candidate comparison (up to 4), **F-020** Compare plants. Per `04-phases.md` M3.2 also: characteristics panel, DoF meter, conflict panel, quick-entry drawer (`07-characteristics.md` §6). Spec refs: `03-ui.md` §1, §4A–C, §8; `07-characteristics.md` §1, §4, §6; `01-domain.md` §4.5. M3.1 delivered the engine and API; this milestone is the screen that makes them usable. Profiles (profile picker, "save as profile") are **M3.3**.

## 1. Business objective

A QC engineer opens one screen, states what the concrete must do (strength, exposure, slump, NMAS, pumpability) and any values they want to pin, and either **evaluates a mix they typed** or **generates up to five trial candidates**; inspects each with its evidence, validator report and compliance table; compares up to four; and sends one to trial. The screen never lets a candidate look approved, never hides why a request is blocked or conflicting, and shows cost only to roles that may see it.

## 2. Scope

**In scope**

1. **Studio shell and stages (F-018).** Route `/studio`. Header shows the entry path (**Evaluate existing mix** | **Generate trial recommendation**) and the current stage; stages **Requirements → Candidates → Inspect & Validate → Save / Request trial**. Desktop shows adjacent stages as panes; the current stage is always obvious; tablet and mobile (read-only on mobile) per `03-ui.md` §1. Draft Studio state survives a reload (local draft only; nothing is stored until Save).
2. **Requirements stage.** Strength picker (MPa / cube / B-grade with the `strength.basis_map` conversion shown), plain-language exposure picker (icon cards → F/S/W/C chips; F1–F3 shows "air-entrained designs are not supported yet" and disables Generate), code mode ACI | JS | Both, slump, NMAS, pumpable, material pool as chips by category defaulting to materials usable at the plant (excluded ones show the optimizer's reason), plant selector. In Evaluate mode this stage also takes the proportions (reusing the M2.2 editor grid).
3. **Characteristics panel (07 §6).** Sections: Strength & durability · Binder & water · Aggregates · Fresh properties · Economics. Each row: Auto | Fixed | Range | Target, units, origin badge (Request or Code bound; profile badges arrive in M3.3), the live code/project bound beside the input ("≤ 0.45 · ACI S2"). A value that would loosen a code limit is **rejected inline with rule and clause** and never accepted (reuses `POST /api/characteristics/validate`). Objective toggle **Cheapest | Closest to my targets**.
4. **DoF meter and conflict panel.** From the optimizer's `dof`: "N quantities left for the optimizer" / "Fully specified — evaluate only" / "Over-specified". When infeasible: the conflicting characteristics each with the value that would work and a one-click **Release** (sets the characteristic to Auto and re-runs); if only hard rows bind, the panel names them (rule, clause, "binding") with **no saving** attached.
5. **Blocked requests.** `status: blocked` renders the named missing parameters (rule key, what it is, link to the Rules screen, "enter in Rules"), never an empty state or a spinner.
6. **Candidates stage (F-018, F-019).** Ranked cards: cost/m³ in large tabular numerals (cost-visible roles only), Δ vs best, binder, w/cm, margin bars (w/cm headroom, CF, WF, fines, grading), code badges, **evidence chips** (`MODEL_BASELINE`, `TRIAL_REQUIRED`, `RULE_UNVERIFIED`, `USER_OVERRIDE`, `MODEL_PREDICTS_SHORTFALL`), "6 of 7 characteristics met", slump-at-risk note. Pin up to 4 → side-by-side comparison table with differences highlighted. Guardrail shadow prices ("what-ifs") shown to QC roles with cost access only, labelled **hypothetical**. A persistent banner: "Candidates are trial proposals, not approved mixes."
7. **Inspect & Validate.** Tabs: Proportions (kg/m³, L/m³, volume, JOD/kg, JOD/m³, % of cost; totals Σ volume = 1.000 ✓) · Compliance (the M2.2 table) · Strength evidence (ACI baseline and f′cr trace; "no plant model yet") · Gradation (log-sieve chart, never mirrored in Arabic, combined curve, target band, individual aggregates toggle; Shilstone CF/WF chart with the target box) · Cost · Traceability · **Validator report** (candidate validator result and the evaluation check, with every compared number). What-ifs limited to what `03-ui.md` allows.
8. **Save / Request trial.** "Save as draft" creates a draft design from a candidate or typed mix; "Request trial" is **enabled only after the validator passed** and calls the M3.1 trial-candidate endpoint; a candidate with `MODEL_PREDICTS_SHORTFALL` shows who may authorize it and asks a QC manager for a reason. Summary of evidence gaps before saving.
9. **Material quick-entry drawer (07 §6).** "+ Enter characteristics" on a material chip opens the existing M1.1 entry form in a drawer with the minimum set highlighted, source selector, attachment, paste-gradation and live FM; "Use for this request only" creates an **ad-hoc material** (M1.1 mechanism) that the optimizer may use for that request only.
10. **Compare plants (F-020).** Runs the same request at every active plant the user may see; the user **confirms the material mapping** by category and specification (default: same category, same name; shown for review); results table: best cost/m³, Δ vs the current plant, per plant status (candidates / blocked / infeasible with the reason). Haul and delivered estimates only if site distance and haul cost exist (they do not yet: shown as "not available"). Cost-visible roles only; every figure labelled theoretical and trial-only.
11. **API additions (small).** `POST /api/design-requests/preview-pool` (which materials are usable at a plant and why not; read-only), `POST /api/designs` (create a draft design from typed requirements and lines, for the Evaluate path; audited), `POST /api/design-requests/compare-plants` (runs the optimizer per plant with a confirmed mapping; stores one request per plant; audited), and `release` is client-side (re-run with the characteristic set to Auto). Candidate `snapshot`-independent view fields already exist.
12. **Quality gate (`04-phases.md`, `07` A4).** A code-loosening characteristic is visibly rejected with its clause; every value shows its origin (Request, Code bound, Declared, Lab, Model).
13. **i18n.** All strings EN/AR with parity tests; Arabic drafts added to `docs/i18n-review.md`; RTL layout, numerals isolated; the gradation axis stays LTR.
14. **Tests.** Web unit tests (stage logic, DoF text, release action, rejection display); e2e with axe (EN/AR, light/dark): request → candidates → validator pass → trial candidate; blocked request shows named parameters; conflict → Release → candidates; compare 4; compare plants; cost-blind role sees no cost; F1–F3 disabled. Screens EN/AR × 1440 / 1024 / 390 reviewed.

**Explicitly excluded**

- Profiles, profile picker, "save as profile" (M3.3); trial batches, approval, PDF (M4.x); strength model and results (M4.2/M5.2); savings claims and the Savings ledger beyond M2.2 (M5.1); batch-weight/moisture toggle (M4.2); haul/delivered-cost estimates (need site data); air-entrained designs.

## 3. Assumptions

- With the shipped seeds every real request is **blocked** (grading band, WF bounds, fines cap, pumpable minimum, ASTM C33 limits not on file; JS values not on file). The Studio therefore ships showing named blockers on real data and full candidates only on the synthetic demo data set; I will add synthetic **demo-tenant** engineering parameters (labelled SYNTHETIC, demo tenant only, like the demo test-age limits) so the pilot can see the whole flow. The real seeds stay empty.
- The optimizer runs inside the request (up to 20 s); the UI shows progress and offers **Cancel**, which abandons the response (no server-side cancellation yet).
- Plain-language exposure picker maps to the existing F/S/W/C classes; the mapping text is a draft for Sanad to review.
- Materials are mapped across plants by category + name for Compare plants, always confirmed by the user.

## 5. Engineering-correctness risks

| Risk                                                | Mitigation                                                                                                                                             |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A candidate looks approved or predicted             | Permanent banner, `TRIAL_REQUIRED` and `MODEL_BASELINE` chips on every card and in every tab, no "approve" control anywhere in the Studio, copy review |
| "Release" or a what-if quietly relaxes a hard limit | Release only sets a user characteristic to Auto; hard rows have no control; e2e asserts the conflict panel never offers a code limit as releasable     |
| Cost shown to cost-blind roles                      | API already strips; UI renders nothing for absent fields; e2e as sales/plant roles                                                                     |
| Stale result after the user edits requirements      | Results carry the request id; any edit marks them "outdated" and disables Request trial until re-run                                                   |
| Compare plants maps the wrong material              | Mapping is shown and must be confirmed; unmatched categories block that plant with a reason                                                            |
| Chart misleads (mirrored axis, wrong band)          | Log axis fixed LTR, band from the same parameters the validator used, tested against the report numbers                                                |

## 6. Schema / API / UI impact

- **Schema:** none expected (compare-plants stores ordinary `design_requests`; a `compare_group` uuid column on `design_requests` is the one candidate addition, additive).
- **API:** the endpoints in scope item 11; OpenAPI entries; capabilities `design.write` (generate, evaluate, save), `trial.request` (request trial), `cost.view`, `candidate.authorize` as in M3.1.
- **UI:** `/studio` (new nav entry between Dashboard and Mix Library), characteristics panel, DoF meter, conflict panel, candidate cards and comparison, inspect tabs with gradation and Shilstone charts, quick-entry drawer, compare-plants view. Existing evaluation/compliance components are reused.
- **Engine:** none beyond exporting the exposure → class mapping and the "bounds for this characteristic" helper the panel needs (pure, tested).

## 7. Verification strategy

- Definition of Done commands; web coverage for the new logic; engine coverage stays ≥ 90 %.
- E2E (real API, real browser, demo tenant): the full path request → candidates → validator pass → trial candidate; blocked state; conflict → Release → candidates; shortfall candidate needs a QC manager; compare 4 candidates; compare plants with mapping confirmation; role checks (QC engineer, plant manager, sales); axe in EN/AR light/dark; screens reviewed.
- Quality-gate tests: loosening value rejected with clause; origin shown for every value.
- **Verification note** (in `docs/progress.md`): tests prove the screen shows what the API returns, cannot request a trial without a validator pass, never offers to relax a hard limit and never shows cost to cost-blind roles. They do **not** prove any candidate will perform in your plant, that the synthetic demo parameters resemble yours, or that the Arabic wording is final.

## 8. Rollback / migration

Additive: new route, components and three small endpoints (and at most one nullable column). Rollback = revert the commit; stored requests remain readable through the M3.1 API.
