# M7.1 — Cement classification: strength class and market type

Status: **draft, awaiting approval.** No application code is written until this plan is approved.

Trigger: Sanad's notes — Jordanian cement comes in **strength classes 32.5, 42.5 and 52.5** and **types OPC, PPC, SRC and low-alkali**, and there is also **white cement, available in the same different strengths**. The app does not model any of this today.

## 1. What the app does today

- A cement material has one free-text field, `cement_type` (for example `CEM I 42.5N`), plus mill-certificate numbers: `c3a_pct`, `alkali_na2o_eq_pct`, `mortar_strength_28d_mpa`, `blaine_m2_kg`, `pozzolan_pct`, `limestone_pct`.
- The JS rules list EN 197-1 names (`CEM I 42.5N`, `CEM II/B-P 32.5N`, …); the market names OPC / PPC / SRC / low-alkali exist nowhere.
- **The engine already decides by numbers, not labels** (02-codes §5): sulfate resistance reads `c3a_pct`; nothing reads the free text except the strength-model group (M5.2) and display. That stays: a label never satisfies a requirement.

## 2. Business objective

Let a QC person describe a cement the way the plant and the market do (class and type), pick and filter cements by them, and have the app say so when the label and the mill certificate disagree — without ever letting a label loosen a check.

## 3. Scope

1. **Two structured fields on cement materials** (inside the material test properties, so they are versioned with the test): `cement_kind` ∈ {OPC, PPC, SRC, low alkali, **white**} and `cement_strength_class` ∈ {32.5, 42.5, 52.5}. The free-text `cement_type` stays (certificate wording). Both new fields are optional; a cement without them is flagged in data quality, not blocked.
2. **Label vs certificate consistency (warnings, never decisions).**
   - SRC without `c3a_pct`, or with C₃A above the SR limit in the rules (`cement.sr_definitions.*`): "labelled SRC but C₃A …".
   - Low alkali without `alkali_na2o_eq_pct`, or above a QC-entered limit (new engineering parameter `eng.cement.low_alkali.max_na2o_eq_pct`, **null until QC enters it**): named warning.
   - PPC without `pozzolan_pct`: named warning.
   - Class vs `mortar_strength_28d_mpa`: a 28-day value below the class's EN 197-1 minimum (32.5 / 42.5 / 52.5 MPa) is a warning (the minima are parameters in the rules package, unverified until a QC manager checks them).
3. **Market-name mapping** (rules, SHARED, unverified): OPC ↔ CEM I; PPC ↔ CEM II/x-P (Portland-pozzolana); SRC ↔ CEM I-SR; low alkali ↔ a cement meeting the QC limit above; **white ↔ white Portland cement (a white CEM I)**. Used for display, filters and import suggestions only. White cement takes the same three strength classes (32.5, 42.5, 52.5) and the same consistency checks as any other cement (class vs mortar strength, and the C₃A / alkali numbers when they are on file); nothing about it is assumed from the colour.
   3a. **Colour is never mixed by accident.** A white cement and a grey cement are different materials, so an optimizer run, a design and a strength-model group never silently swap one for the other (the group key already contains the cement material and now its kind and class). A Studio request can say **cement colour: any / white only / grey only** (default: any); "white only" restricts the pool to white cements, because architectural concrete cannot take a cheaper grey cement, and the optimizer would otherwise pick the cheaper grey one.
4. **Where it shows up:** the material form (two selects), the Materials list (columns and filters), the Studio pool chips and candidate cards ("OPC 42.5"), the Library and PDF material tables, the evaluation's data-quality list. The strength-model group uses kind + class (a change of either invalidates an approved model, as a change of cement type does today).
5. **Import suggestions.** The legacy import and the materials matcher propose a kind and class parsed from names such as "OPC 42.5N" or "SRC 32.5"; a person confirms each; nothing is filled silently.
6. **Demo data, seeds, EN/AR strings** (Arabic: إسمنت بورتلاندي عادي، إسمنت بوزولاني، إسمنت مقاوم للكبريتات، إسمنت قليل القلويات; drafts for review), tests, screens, ADR 0018.

**Explicitly excluded:** white-cement colour specifications (whiteness / brightness values), pigments and colour matching (the `pigment` category exists but is not part of this milestone); deciding sulfate, ASR or strength compliance from a label; the early-strength suffix (N / R) unless you want it; mixing cement kinds in one design as a feature; any change to the optimizer's cost or constraints (it still sees the numbers); SCM classification.

## 4. Questions for you (default in brackets)

1. **Strength classes** 32.5, 42.5, 52.5 only [yes]; or also the early-strength suffix N / R [no].
2. **PPC** means Portland-pozzolana cement (CEM II/x-P or IV) [yes].
3. **SRC**: C₃A at most 3 % (SR3) as in the JS taxonomy, with SR5 also accepted by the numbers [yes; the checks still read `c3a_pct`].
4. **Low alkali**: the Na₂O-equivalent limit is yours to enter (a common value is 0.60 %); I leave it empty and name the warning until you do [yes].
5. **Are the two fields required** for a cement to count as complete? [No: optional, shown as a data-quality note, so existing materials keep working].
6. Do any of your cements combine these (for example "SRC 42.5" with low alkali)? [Kind is single-valued; a cement that is both SRC and low alkali is recorded as SRC, and its alkali number is checked anyway].
7. **White cement** is recorded as its own kind ("white"), with the same three strength classes [yes]; or as a colour flag next to the kind, so a white cement can also be OPC or SRC [no].
8. **Studio request option** "cement colour: any / white only / grey only" [yes, default any].
9. Which strengths does your white cement actually come in (all of 32.5, 42.5, 52.5, or only some)? [all three are allowed; tell me if only some exist, and I will limit the choice].

## 5. Risks and mitigations

| Risk                                    | Mitigation                                                                                      |
| --------------------------------------- | ----------------------------------------------------------------------------------------------- |
| A label is trusted over the certificate | No check reads the label; tests prove a mislabelled cement still fails or passes on its numbers |
| Existing materials break                | Fields optional; the schema stays additive; old tests keep validating                           |
| Wrong class limits invent a "failure"   | Class minima are rules, unverified until QC verifies; a violation is a warning, not a hard fail |
| Import guesses wrongly                  | Suggestions only, confirmed by a person, never auto-applied                                     |

## 6. Schema / API / UI impact

No database migration (properties are JSON). Engine: property schema, data-quality items, strength-group key. Rules seeds: market mapping, class minima, low-alkali parameter (null). API: validation messages. Web: material form, Materials list, Studio chips, import suggestions.

## 7. Verification

Definition of Done commands; property tests (a label never changes a check result); unit tests for each consistency warning on both sides of its threshold; API and e2e (axe, EN/AR); screens. The verification note will say what is **not** proven: that your cements' real certificates match their labels.

## 8. Rollback

Revert the commit; stored properties keep the extra keys harmlessly (they are only read by the new code).
