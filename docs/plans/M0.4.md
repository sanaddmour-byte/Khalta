# M0.4 — Rules package

Status: **draft, awaiting approval.** No application code is written until this plan is approved.

Features in scope (from `06-features.md`): **F-003** Rules library (ACI/JS) with verification workflow and JS CSV import; **F-004** Both mode and PROJECT layer (tighten-only). Also the small M0.1 follow-up introduced by Addendum A1: `pnpm features:check`.

## 1. Business objective

Make every code and engineering value a piece of **data with provenance**: where it came from, what it applies to, whether a QC manager has checked it against the licensed document. The engine (M2.1+) will only ever read values through the resolver built here, so "Both" mode, project overrides and the "no approval on unverified rules" safeguard are enforced in one place and tested exhaustively. This milestone also decides how the app can tell a consultant "this limit comes from ACI 318-19 T19.3.2.1" with a straight face.

## 2. Scope

**In scope**

1. **Rule schema** (`packages/rules`, Zod): key, kind (the ten kinds in Appendix A), requirement_class (the six v4 classes plus `USER_SPECIFIED` from Addendum A1, which seeds never use), applies_to, prerequisites, value / `null` / `inherits: "ACI:<key>"`, structured table data (rows, cols, data, interpolation), units, clause_ref, source_doc, edition, valid_from/valid_to, note_ar/note_en, optional `group` (chapter, for the UI), verified flag.
2. **Seeds** transcribed from `02-codes.md` §4–§6, all `verified: false`: `aci/` (sulfate thresholds, durability T19.3.2.1, air T19.3.3.1, SCM limits, max NMAS fractions, f'cr constants, acceptance, ACI 211.1 tables as `DESIGN_AID`, C94 slump tolerance, hot weather), `shared/` (strength basis map, cross-code cement equivalence), `js/` (a skeleton of **every** rule key with `value: null`, `clause_ref: "JSC-2022 §TBD"`, plus the JS 30-1 cement taxonomy and EN 197-1 SR definitions), `engineering/` (parameters from §6, starter values or `null`).
3. **YAML loader and validator** with a clear error per file/rule; duplicate-key, unknown-kind, wrong-unit and bad-table-shape detection.
4. **Resolver** (pure, no I/O): given a ruleset mode (ACI / JS / BOTH), project overrides and a context (exposure classes, strength, NMAS, air-entrained, …) it returns, per requirement, the governing value with its **source, clause, class and verification status**, per-source values, and explicit `unresolved` entries (never silently dropped). Implements `02-codes.md` §3 semantics for every kind, the PROJECT layer (tighten-only; loosening is rejected with the governing rule and clause), applicability matching, null handling ("missing is never evidence the other side suffices"), and the approval-gate helper `unverifiedDependencies(resolved)`.
5. **Database + API:** tables `rulesets`, `rules` (versioned rows), `rule_verifications` (append-only history with the typed e-signature note), `rule_import_batches`; idempotent `rules:sync` from seeds; endpoints to list/read rules, verify a rule, import JS values (preview → commit), and read resolver output for a context (used by later milestones and by the UI's "what applies" panel). All mutations are audited (`withAudit`), tenant-scoped, RBAC-gated.
6. **Rules screen** (replaces the placeholder): grouped by ruleset → chapter, value, class, clause, verification badge, "used by N designs" (shows 0 until designs exist), filters by code/class/status, table-rule viewer (e.g. ACI 211.1 grids), verify dialog with typed e-signature note (QC manager only), engineering-parameters section, **CSV import with validation preview**, banner explaining that unverified values are transcription candidates. Full AR/EN, RTL-correct, evidence/status chips.
7. `templates/js-rule-values.csv` (Appendix D) and `pnpm features:check` (validates `06-features.md` and lists approved features for the active milestone).
8. **ADR: rule normalization and Both-mode conflict handling** (required by `CLAUDE.md`).

**Explicitly excluded**

- Any engineering computation using the rules (f'cr, w/cm, water demand: M2.1+). The f'cr constants and tables are only stored.
- The characteristics resolver and request/profile layers (M2.1, M3.3). M0.4 only makes sure the resolver's output shape (`governing bound + clause`) is what Addendum A1 §1.3 needs to reject loosening characteristics later.
- Project-override entry UI (Studio, M3.2); the resolver supports overrides, the API accepts them in the resolve call, no screen edits them yet.
- Excel import for rules (CSV only), rule deletion (rules are superseded, never deleted), multi-edition handling beyond `valid_from/valid_to`.
- EN 206 ruleset content (must be addable with seed files only; proven by a test fixture ruleset, not shipped content).

## 3. Assumptions

- `02-codes.md` §4–§6 is the authoritative **starting transcription**; I do not know whether every number matches the licensed ACI/JS documents and will not "correct" any from memory. Differences found later are fixed through the verification/edit flow (Q1), not silently.
- Exposure classes combine: a request with several classes (e.g. F0, S1, W0, C1) takes the strictest applicable limit per quantity (max w/cm → lowest, min f'c → highest, prohibitions → union). This is how the spec's merge table composes with exposure.
- Rule `kind` and `requirement_class` drive behaviour; `group` (chapter) is presentation only.
- New libraries (approved list): `yaml`, `zod` (already used), `papaparse` (CSV), `fast-check` (property tests). No ADR needed for them.
- JS clause references and values arrive as a CSV from Sanad; until then every JS row is `null`, so **Both/JS mode runs provisionally on ACI values and blocks approval** by design.
- Time zone and number display follow the existing app rules; clause references are shown in LTR isolation (`Ltr`).

## 5. Engineering-correctness risks

| Risk                                                                        | Mitigation                                                                                                                                                                                                                                                     |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Transcription errors** in seeds look authoritative on screen              | Every seed is `verified: false`; UI banner and chips; cross-check test parses the actual tables in `02-codes.md` and compares every number to the seeds (catches seed ↔ spec drift, not spec ↔ standard drift, which only QC verification can catch)           |
| A resolver bug makes Both mode **less** strict than either code             | Property tests (fast-check) over generated rule pairs: Both ≥ strictest of {ACI, JS} for every kind; PROJECT result never looser than the base; fixture tests for each merge kind and for conflict-empty cases (disjoint sets/ranges → infeasible with reason) |
| Null on one side treated as "no limit"                                      | Explicit tests: the known side drives a _provisional_ result flagged `unresolved_other_side`; approval gate blocked; surfaced in output and UI                                                                                                                 |
| Verification **survives a value change** (a checked value silently altered) | Changing a value (import or edit) creates a new rule version with `verified=false`; verification history keeps the old record; test asserts it                                                                                                                 |
| Self-verification (the person who typed a value signs it off)               | Four-eyes on verification against the last editor (Q3); seeds count as system-authored                                                                                                                                                                         |
| Unit confusion (MPa vs kg/cm², ppm vs %)                                    | Schema requires `units` from a closed list; CSV import rejects unit mismatch against the skeleton; conversion happens only in the documented basis map                                                                                                         |
| Interpolation of design-aid tables outside their range                      | Table schema declares domain and policy (`linear`, no extrapolation); lookup returns `out_of_domain` instead of a number; tested at and beyond the edges                                                                                                       |
| Applicability mistakes (an S2 rule applied to F1)                           | `applies_to` matching is pure and unit-tested per seed; a test enumerates every exposure class and asserts exactly the rules the spec table implies                                                                                                            |
| Loosening project override accepted                                         | Override validation compares against the resolved base per kind; rejected with rule + clause; tested for every kind, and at the API                                                                                                                            |
| `DESIGN_AID` tables presented as compliance                                 | The class flows through to outputs; output type forbids `DESIGN_AID` as compliance (type-level + test)                                                                                                                                                         |
| Seed/DB divergence after QC edits                                           | Decision in Q1 + ADR; drift report command; sync never overwrites a QC-edited or verified value                                                                                                                                                                |

## 6. Design notes (to be recorded in the ADR)

- **Normalized rule model:** one row per rule per ruleset; tables are rules of kind `table` with a typed grid; `inherits` resolves at load time to a _reference_, not a copy (so verifying the ACI value does not verify the JS row, which has its own `verified`).
- **Kinds → merge:** `limit_max` (min of values), `limit_min` (max), `allowed_set` (intersection; empty → infeasible with reason), `prohibition` (union), `range` (intersection per sieve), `tolerance` (tighter), `table` (never auto-merged; needs an explicit applicability policy, otherwise a named blocker), `info` (listed, never a constraint), `parameter`/`value` (single-source; conflicting sources → blocker).
- **Layers:** CODE (by mode) → PROJECT (tighten-only). Request/profile layers from Addendum A1 plug in later using the same "tighten-only against resolved base" function.
- **S3 options:** ACI T19.3.2.1 gives two alternatives for S3 (w/cm 0.45 with Type V + pozzolan/slag, or 0.40 with Type V). Modeled as two rule variants keyed by an `option` context value; a request that is S3 without an option gets a named blocker (Q2).
- **Provenance in output:** every resolved item carries `{ruleId, version, source, clause_ref, requirement_class, verified}`; "governing" is explicit, never inferred by the caller.

- **UI:** Rules screen as described; nav item already exists and is role-aware.
- **RBAC:** one new capability `rules.read` (Q4), added to the matrix and the generated tests.

## 8. Verification strategy

- DoD commands green: `typecheck`, `lint`, `test`, `test:rules`, `e2e`; zero serious axe violations; `pnpm screens` AR/EN × 1440/1024/390 reviewed against the §8 checklist.
- `pnpm test:rules`: schema validation of all seed files; **cross-check against `02-codes.md`** (parsed tables); every JS rule key present and `null`; every seed `verified: false`; no seed value duplicated in TypeScript (a test greps the packages for the numeric constants).
- Resolver: example tests per kind, edge cases (empty intersection, null side, S3 options, multi-exposure), **property tests** (Both never looser, PROJECT tighten-only, resolver deterministic, order-independent).
- API tests against real Postgres: RBAC matrix extension, audit rows, verification invalidation on value change, four-eyes on verification, CSV preview/commit including malformed files and unit mismatches, idempotent `rules:sync`, tenant isolation.
- E2E: QC manager verifies a rule (e-signature note required), QC engineer cannot see the verify action, CSV import preview with an error row, EN/AR, drawer/dialog direction, axe.
- **Verification note** (recorded in `docs/progress.md`): tests prove the seeds match the spec text, the resolver implements the documented semantics, and verification state is tamper-resistant. They do **not** prove any value matches ACI or the Jordanian code; only a QC manager's verification against the licensed documents does, and green tests never change a rule's verified status.
